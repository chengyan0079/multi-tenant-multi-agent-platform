# 数据库变更与发布治理智能体 · 执行方案

> 定位：基于「多租户多 Agent 协作平台」底座，落一个**差异化、有真实感**的业务场景——面向企业内部研发/DBA 的数据库变更与发布治理中台。本文档同时服务两个目标：**① 指导代码实现（从底座到 5 个 Agent 分阶段落地）；② 面试可讲（架构、分支边、HITL、并行、安全两套防护）。**

---

## 0. 文档目的与范围

- **做什么**：在已有平台底座（六层 + AgentRegistry + Orchestrator + 检索内核 + 工具层 + HITL/恢复）之上，接入 5 个业务 Agent（含 1 个 RAG），构成「数据库变更与发布治理」场景。
- **不做什么**：不碰 NL→SQL（Text2SQL）；不做客服/BI/招聘等烂大街场景；不自动执行高危 DDL（必须 HITL）。
- **交付节奏**：先代码实现（阶段 0–7），再据此准备面试（第 9 节）。

## 1. 场景定位与价值

**一句话定位**：审人写的 SQL、管变更发布——评审风险分级 →```
SET search_path TO unified_schemas;
BEGIN;

ALTER TABLE agent_db_connection ADD COLUMN IF NOT EXISTS env VARCHAR(16) NOT NULL DEFAULT 'prod';
COMMENT ON COLUMN agent_db_connection.env IS '环境：prod / staging / sandbox';

CREATE TABLE IF NOT EXISTS agent_change_release (
    id BIGSERIAL PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    request_id BIGINT NOT NULL,
    sandbox_connection_id VARCHAR(64) NOT NULL,
    exec_ok BOOLEAN,
    exec_ms INTEGER,
    affected_rows BIGINT,
    error TEXT,
    sandbox_rolled_back BOOLEAN,
    final_sql TEXT,
    status VARCHAR(24) DEFAULT 'verifying' NOT NULL,
    trace_id VARCHAR(64),
    create_at TIMESTAMP(0) WITHOUT TIME ZONE DEFAULT date_trunc('second', now()) NOT NULL,
    updated_at TIMESTAMP(0) WITHOUT TIME ZONE DEFAULT date_trunc('second', now()) NOT NULL,
    create_user_id BIGINT,
    update_user_id BIGINT,
    create_tenant_id BIGINT,
    update_tenant_id BIGINT
);
CREATE INDEX IF NOT EXISTS idx_change_release_tenant ON agent_change_release (tenant_id);
CREATE INDEX IF NOT EXISTS idx_change_release_request ON agent_change_release (request_id);

COMMENT ON TABLE "agent_change_release" IS '变更发布（db_release 沙箱验证）';

COMMIT;
``` 灰度执行 → 异常回滚，全程人工门禁。

**为什么适合（你的底子）**：11 年 Java/支付信贷保险生产经验，真干过大表加字段、跨库事务、锁等待、主从延迟。场景不假，辨识度来自「没人讲数据库变更治理」。

**辨识度来源**：DBA 变更审批 + 高危 DDL 管控是硬刚需；HITL 落点极其自然（不可能让 AI 自动 DROP 表）。

**多租户映射**：tenant = 不同业务库 / 研发团队 / 审批链，靠三层隔离（PG `tenant_id` 行级 / Milvus 分区键 / Redis 键前缀）零串扰。

## 3. 各 Agent 详细规格

### ① RAG 变更规范库问答 Agent（必含 RAG）
| 项 | 内容 |
|---|---|
| 功能 | 接共享检索内核（父子块+BGE-M3 双路+RRF k=60+rerank top5），答规范/Online DDL 安全做法/回滚预案模板/历史事故/锁处理；FAQ 优先+RAG 兜底+溯源 |
| 分支边 | ① FAQ 命中(命中零 LLM) ② 生成置信达标/不达标 |
| HITL | 低置信 `interrupt(low_conf)`，状态按 `thread_id` 落库，人工补充分流「待补充队列」 |
| 恢复 | `Command(resume)` 断点增强检索/重生成；暂停前不写数据，结果幂等留痕 |
| 平台复用 | tenant_id 分区检索；Embedding/Reranker 进程单例常驻 |

### ② 变更评审 Agent（风险分级）
| 项 | 内容 |
|---|---|
| 功能 | 接收提交 SQL(DDL/DML)，静态评审：表大小/行数估算、是否 Online DDL、预估锁时长、是否影响核心链路、跨库事务、回滚预案完整性。**只分析不执行** |
| 分支边 | 风险等级→低(自动过)/中(PM 审批)/高(DBA+架构师)/极高(CTO+演练) |
| HITL | `interrupt(change_approve)` 中高审批；极高需附回滚演练记录 |
| 恢复 | 不通过回退草稿(隔离不碰主库)重提；`Command(resume)` 续审 |
| 平台复用 | 元数据读取走 Agent⑤(只读)；token 预算 2000 |

### ③ 灰度执行 Agent
| 项 | 内容 |
|---|---|
| 功能 | 按策略灰度落地：大表从库/影子先验证，或 Online DDL 分批，或 DML 按主键范围分批；每阶段验证(主从延迟/锁等待/写入 QPS)再推下一步 |
| 分支边 | ① 每阶段成功/失败 ② 灰度指标达标/不达标 ③ 是否需人工门禁 |
| HITL | `interrupt(gate_approve)` 灰度转全量门禁；异常人工决策继续/中止 |
| 恢复 | 失败自动回滚上一稳定 checkpoint 或暂停等人工；`Command(resume)` 断点续 |
| 平台复用 | 具体 SQL 委托 Agent⑤；trace_id 贯穿 |

### ④ 回滚编排 Agent
| 项 | 内容 |
|---|---|
| 功能 | 变更异常触发回滚预案：撤销 DDL(删索引)/补偿 DML(反向 SQL)/恢复配置；支持自动(有预置反向 SQL)或需审批 |
| 分支边 | ① 是否有预置反向 SQL(可自动/需审批) ② 回滚成功/失败 |
| HITL | `interrupt(rollback_approve)` 高危回滚审批 |
| 恢复 | 回滚失败重试/断点 resume；状态 `AsyncPostgresSaver` 持久化 |
| 平台复用 | 与 Agent① 共享检索内核(查回滚预案)；SSE 可服务端中止 |

### ⑤ 工具执行 Agent（信任边界）
| 项 | 内容 |
|---|---|
| 功能 | 被委托执行：执行 SQL、锁监控(`SHOW PROCESSLIST`/`information_schema`)、慢查询 `EXPLAIN`、主从延迟、调审批系统；插件协议定义能力、扫描登记能力表 |
| 分支边 | ① 选哪个工具(能力表匹配) ② 安全校验(白名单/危险操作拦截) ③ 成功/失败 |
| HITL | 高危命令 `interrupt(danger_approval)` 审批(DROP/TRUNCATE/无 WHERE 的 UPDATE) |
| 恢复 | 超时重试上限→进死信队列(RabbitMQ DLQ)；注册表运行期重建 |
| 平台复用 | 直接对应简历「工具层插件协议+能力表+运行期重建注册表」 |

## 4. 编排设计：串行主干 + 并行分支

**必须串行（因果依赖）**：评审 → 执行 → 回滚；灰度 → 全量。这部分是 Supervisor 的串联 Pipeline。

**可并行（无依赖）的 6 类场景**：

| # | 并行场景 | 并行子任务 | 聚合点 | LangGraph 机制 |
|---|---|---|---|---|
| 1 | 评审前并行预检 | 锁影响/行数估算/历史事故检索/规范校验/当前负载 | 全过才出风险评级 | `async` 并发 + fan-in |
| 2 | 灰度后并行监控 | 主从延迟/锁等待/写入 RT·QPS/错误率 | 全达标才放灰度门禁 | 并行观测+与门 |
| 3 | 多分片并行执行 | 同 DDL 扇出 N 副本/分片 | 收集各实例结果 | `Send()` 动态扇出 |
| 4 | 多租户并行发布 | 同 schema 变更对租户 A/B/C 独立执行 | 每租户独立 checkpoint | 并行分支+隔离 |
| 5 | RAG 内部并行召回 | 向量+BM25 双路；多 Sub-query 变体 | RRF 融合 | 并行 retrieve+merge |
| 6 | 回滚并行补偿 | 删索引 A+B+反向 DML(互不依赖) | 全补偿完才标记恢复 | 并行补偿节点 |

**LangGraph 落地**：`async` 节点并发；`Send()` 动态扇出 + Supervisor fan-in；并行分支 `add_edge` + 聚合 `conditional_edges`；并行分支 `interrupt()` 各自 checkpoint，`Command(resume)` 从所有断点续跑，失败隔离。

## 5. 安全与资源防护（关键，面试必讲）

### 5.1 元数据泄露防护（6 层）
| 层 | 措施 | 作用 |
|---|---|---|
| 1 | 模型私有化/内网部署 | LLM 跑 VPC 内，数据不出网 |
| 2 | LLM 不收原始元数据，只收结构化结论 | 工具层本地分析，只回传行数/索引数/预估锁时长等数字 |
| 3 | 标识符脱敏令牌化 | `t_payment_settle→TBL_001`；LLM 在令牌上推理，仅工具层回映射 |
| 4 | 最小权限只读账号 | Agent 用独立 read-only metadata 账号，禁 sample rows |
| 5 | 信任边界/网络隔离 | 工具层与元数据库同安全组；RAG 存人工编纂规范，非自动抓生产元数据 |
| 6 | 全链路审计 | 每次查询记"谁/什么/何时"，Langfuse+DB 审计可追责 |

**核心澄清**：直接把 `CREATE TABLE` 原文丢公网 LLM 是泄露——设计上**禁止**。LLM 看到的是结构性数字，表名/列名/样本数据留边界内。

### 5.2 连接池 / 生产安全（6 层）
| 层 | 措施 | 作用 |
|---|---|---|
| 1 | 专用只读账号+独立连接池 | Agent 自己池(限 2–4 连接)，不占生产池 |
| 2 | 读从库/影子库，零碰主库 | 监控/元数据全走副本 |
| 3 | 连接配额+限流 | Token-bucket 限 QPS/max 并发，超额排队拒绝 |
| 4 | 查询级防护 | `READ ONLY`+`MAX_EXECUTION_TIME` 超时+慢查询自动 kill |
| 5 | 熔断 | 副本延迟/DB 负载超阈值→电路断开，诊断暂停 |
| 6 | 元数据缓存 | schema 稳定→Redis 按租户键前缀缓存+TTL，DDL 事件刷新 |

**统一执行点 = 工具执行 Agent**：它既是执行器，也是信任边界网关——对内接 DB(专用只读池+从库路由+脱敏令牌)，对外只吐结构化结论。所有 DB 操作收口一处，安全与配额只在一处管控。

## 6. 技术栈与依赖

- **编排**：LangGraph（`StateGraph`/`Send()`/`interrupt`/`Command(resume)`）、LangChain
- **持久化/恢复**：`AsyncPostgresSaver`（checkpoint，`thread_id` 断点）
- **检索内核**：Milvus（分区键）+ BGE-M3（稠密/稀疏）+ RRF k=60 + reranker top5
- **缓存/隔离**：Redis（键前缀按 tenant_id）
- **配置热更**：Nacos（Prompt/模型/规则/审批链，支持审批回滚）
- **可观测/成本**：Langfuse（CallbackHandler 采 token）、`token_usage`/`latency_ms` 逐轮落库
- **死信**：RabbitMQ DLQ（工具超时重试达上限）
- **模型**：4 类（LLM/Embedding/Reranker/Classifier），按启用记录驱动，未启用不加载
- **输出**：统一入口 SSE 流式事件

## 8. 注册架构改造 + 4 个新 Agent 详细设计

### 8.1 注册改造：DB 唯一注册源，去路径扫描
**现状**：`base.Agent.__init_subclass__` 自动登记 + `agents/__init__.py` 的 `pkgutil` 遍历子包 import + `orchestrator_manager` 注册后 `registry.start()` 读库，DB 只做元数据开关。

**目标**：注册唯一来源 = `agent` 表（`tenant_id` + `enabled`）；启动直接读库；变更自动 reload；**移除 pkgutil 路径扫描**。

**改造点**：
- `backend/agents/__init__.py`：删除 `load_agent_modules()` 的 `pkgutil.iter_modules` 遍历；改为**显式构造器表** `AGENT_BUILDERS: dict[str, type[Agent]]`（各 agent 模块显式 import 后登记，不依赖目录/命名）。
- `orchestrator_manager.start()`：不再 `iter_agent_classes()` 全量注册；直接 `await registry.start()`（内部读 DB）。
- `AgentRegistry.load_from_db()`：读 `agent` 表 → 对**每个 `enabled=true` 的 `(tenant_id, agent_type)`**，从 `AGENT_BUILDERS` 取构造器构建 meta；DB 无记录/未启用 → 不注册（即使代码有构造器）；无构造器 → 告警跳过。
- `refresh()`：reload DB（已有）；`publish_config_refresh("agent_registry")` 通知多副本（已有）。
- 启动：`registry.start()` 首次 load；**DB 为空的 agent_type 一律不生效**。

**新 Agent 添加方式（两档）**：
- **A（推荐，自定义 graph）**：新增 `backend/agents/<type>/`（agent.py/graph.py/state.py/nodes.py/prompts.py），在 `AGENT_BUILDERS` 显式加一行；DB `agent` 表插入 `(tenant_id=0, agent_type, enabled=true)`。运营按租户绑定后生效。
- **B（完全配置化，可选）**：通用 `ConfigurableGraph` 读 DB 的 graph 配置（节点/边/prompt/模型），适合简单 pipeline；HITL/并行复杂场景仍用 A。

> 结论：**"注册/租户/启停/提示词/模型/工具"全部 DB 驱动；graph 构造是代码能力（按 agent_type 静态映射），不再靠路径扫描。**

### 8.2 新增数据库表
| 表 | 关键字段 | 用途 |
|---|---|---|
| `agent_change_request` | id, tenant_id, user_id, thread_id, title, target_db, db_type, sql_text, risk_level, status, trace_id | 变更单主表 |
| `agent_change_review` | id, request_id, risk_level, online_ddl, lock_estimate_ms, affected_rows, core_path, cross_db, rollback_ready, detail(JSONB), status | 评审结果 |

**状态流转**：
- `request.status`：`draft → reviewing → pending_approval → approved → releasing → released / failed → rolling_back → rolled_back / rolled_back_failed`

### 8.3 Graph 流程设计（LangGraph）
**② db_review（变更评审）**
```
entry → load_request
 → Send 并行预检(fan-out)：lock_impact / rows_estimate / history_incident(RAG) / spec_check(RAG) / current_load(db_tool)
 → fan-in(aggregate) → risk_grade(LLM 结构化输出)
 → 低风险 → persist_done
 → 中/高 → interrupt("change_approve") → approval → persist
 → END
```
state：`request_id, sql_text, target_db, prechecks, risk_level, approval`。

**③ db_release（灰度执行）**
```
entry → load_approved_request → plan_phases(LLM)
 → 循环每个 phase：
     execute_phase(委托 db_tool)
   → Send 并行监控(fan-out)：replication_lag / lock_wait / write_qps / error_rate
   → fan-in verify → 达标？
        非最后阶段 → interrupt("gate_approve") → 下一阶段
        最后阶段   → 全量 → persist_released
     不达标 → interrupt("gate_approve") 人工决策 / 触发 rollback
 → END
```

**④ db_rollback（回滚编排）**
```
entry → load_request → has_reverse_sql?
  auto   → Send 并行补偿(reverse_dml / drop_index / restore_config) → fan-in verify → persist
  manual → interrupt("rollback_approve") → execute → verify
  失败 → retry(上限) → RabbitMQ DLQ
```

**⑤ db_tool（工具执行 / 信任边界）**
```
entry → match_capability(能力表) → safety_check(白名单/危险操作拦截)
  → 高危(DROP/TRUNCATE/无 WHERE UPDATE) → interrupt("danger_approval")
  → execute(只读池/沙箱) → 结构化结果
  超时重试上限 → DLQ
```

**① qa（复用）**：保留现有 RAG 检索；替换知识库（规范/事故/回滚预案）+ `prompts.py`；FAQ 命中直出、低置信 `interrupt("low_conf")`。

## 9. Agent 模板抽象（低侵入，先行）

> 目标：新增 Agent 从「5 文件 + 手写 `StateGraph` 装配」简化为「1 个 `agent.py` 声明 `metadata` + `flow`（+ 可选 `nodes/prompts`）」，**不改动现有 `qa`**。

### 9.1 新增 `backend/agents/template.py`
- `BaseAgentState`：公共状态字段（`messages/tenant_id/user_id/session_id/query`）。
- `FlowSpec`：声明 `nodes / entry / edges / conditional / end_nodes`。
- `hitl_node(gate, payload_fn)`：生成 `interrupt` 门禁节点（审批上下文只放结构化结论）。
- `AgentTemplate(Agent)`：统一 `build_graph()` 基于 `FlowSpec` 装配 + `checkpointer`；`input_schema` 默认 `None`；子类实现 `metadata()`、`state_cls`、`flow()`。

### 9.2 新增 Agent 示例（评审 Agent）
```python
class DbReviewAgent(AgentTemplate):
    agent_type = "db_review"
    state_cls = DbReviewState

    def metadata(self) -> AgentSpec:
        return AgentSpec(agent_type="db_review", display_name="变更评审", ...)

    def flow(self) -> FlowSpec:
        return FlowSpec(
            nodes={
                "load": load_node,
                "precheck": precheck_node,   # 内部可用 Send() 并行预检
                "grade": grade_node,
                "approve": hitl_node("change_approve"),
                "persist": persist_node,
            },
            entry="load",
            edges=[("load", "precheck"), ("precheck", "grade"), ("approve", "persist")],
            conditional=[("grade", route_risk, {"low": "persist", "high": "approve"})],
            end_nodes=["persist"],
        )
```

### 9.3 兼容与收益
- **兼容**：`qa` 等既有 Agent 保持各自 `build_graph`，模板为增量能力，不强制迁移。
- **收益**：新增 Agent 只需声明「状态 + 流程 + 元数据」，图装配、checkpointer、HITL 门禁统一由模板处理；并行 `Send()` 可在节点内实现，模板不限制。
- **与注册改造衔接**：模板子类仍继承 `Agent`（自动登记）；后续第 8.1 节「DB 唯一注册源」只需在 `AGENT_BUILDERS` 收集模板子类，不需改模板本身。

## 10. 模板的生产级能力（多轮/记忆/上下文/提示词/幂等/HITL）

### 10.1 多轮对话
- `state.messages` 用 `add_messages` 增量合并；`thread_id = t{tenant}:u{user}:{session}`，会话级 checkpoint。
- 每轮 `turn_id` 唯一；`history_window`（默认 6）控制近 N 轮；超长走 `existing_summary` 摘要，避免上下文无限膨胀。
- `TurnContext` 统一承载 `tenant/user/session/turn/thread`，作为幂等与隔离键。

### 10.2 记忆
- **读**：`before_turn` 读 `agent_long_term_memory`（`tenant+user+agent_type`）与会话摘要，注入 `state`。
- **写**：`after_turn` 走 `long_term_memory_extractor` 抽取写入；**仅在有信息增量时写**，避免噪声。
- **隔离**：严格按 `tenant_id`/`user_id`，禁止跨租户；记忆写失败降级不阻断主链路。

### 10.3 上下文（token 预算）
- 组装顺序：`system → 长期记忆摘要 → RAG top5 → 近 N 轮历史 → 当前输入`。
- `context_token_budget`（默认 4000）：超预算**先裁历史、再裁检索**，保留 system 与当前输入。
- 工具结果只回传结构化数字（行数/锁时长/延迟），不放原始 SQL/表名（脱敏）。

### 10.4 提示词
- `prompts` 常量 + `render_prompt(name, **vars)`；可由 DB/Nacos 覆盖（版本化，支持回滚审批）。
- 输出强约束 JSON schema；HITL 文案与 `ERROR` 兜底统一由模板约定。

### 10.5 并发与幂等
- **幂等键**：`idempotency_key = {agent_type}:{thread_id}:{turn_id}`；Redis `SETNX` 去重，重复提交直接返回上次结果。
- **同 thread 串行**：Redis 分布式锁（`thread_id`），防同会话并发交错；锁超时释放。
- **节点幂等**：写库 `INSERT ... ON CONFLICT` / 状态机 CAS（`status` 条件更新），重复执行不产生副作用。
- **resume 幂等**：审批表 `(request_id/thread_id, gate)` 唯一，重复 `resume` 不重复生效。

### 10.6 HITL 打断与恢复
- `interrupt` 前**不写业务数据**；状态由 `AsyncPostgresSaver` 持久化；`Command(resume)` 续跑。
- 恢复校验：审批人/租户/权限/超时；`hitl_timeout_s`（默认 1800）超时由调度置「拒绝/转人工」。
- 并行分支各自 checkpoint，`resume` 从所有断点续；单分支失败隔离，不影响其它分支。
- 前端审批页 → `POST .../approve` → `resume`，审批留痕落 `agent_approval`。

### 10.7 失败与可观测
- 节点异常重试上限 → `RabbitMQ DLQ`；`trace_id`/`token_usage`/`latency_ms` 逐轮落库 + Langfuse。
- 工具调用超时/熔断；只读连接池限流；审计每次查询「谁/什么/何时」。

## 11. 上下文压缩 / Trace / 审计 / 观测

### 11.1 上下文压缩（防上下文膨胀）
- **滑动窗口**：`history_window`（默认 6）只保留近 N 轮对话。
- **token 预算**：`context_token_budget`（默认 4000），从旧到新累计，超预算丢弃更早消息。
- **单条截取**：`truncate_text(text, max_chars, keep_tail)` 保留首尾、中间省略，避免丢关键信息。
- **组合顺序**：消息窗口压缩 → 单条截取 → 再加 `system/记忆/RAG/当前输入`；裁剪优先级「历史 < 检索 < system/当前输入」。
- **摘要兜底**：超长会话走 `existing_summary`（`long_term_memory_extractor` 生成），不无限堆历史。

### 11.2 Trace（全链路追踪）
- `TurnContext.trace_id` 贯穿：入口生成 → 节点/工具/LLM → 落库/日志。
- `trace_span(name, **attrs)`：节点级结构化 span（start/end/error 日志埋点）。
- `invoke_config(ctx)`：LangChain 调用带 `metadata={trace_id, tenant_id, user_id, agent_type, session_id, turn_id}`。
- 跨服务/队列：`trace_id` 随 broker 消息头传递（已有 `MessageHeader`）。

### 11.3 审计（可追责）
- `audit(ctx, action, result, **extra)`：结构化记录「谁 / 什么 / 何时 / 结果 / trace」。
- 审计域：变更提交、评审结论、审批决议、灰度阶段、回滚动作、工具高危调用。
- 落库：`agent_audit_log`（已有 DAO）+ `agent_approval`（HITL 留痕）；失败降级不阻断主链路。
- 敏感信息：审计只记结构/令牌，不记原始 SQL 元数据。

### 11.4 可观测（对接 Langfuse）
- `get_langfuse_handler()`：按配置（`LANGFUSE_*`）返回 `CallbackHandler`，未配置自动降级 `None`。
- `invoke_config()` 把 callback 注入每次 LLM 调用，采 token/延迟/父子 span。
- 逐轮落库：`token_usage / latency_ms / trace_id / agent_type`（现有表）。
- 关键指标：评审耗时、灰度阶段成功率、回滚触发率、HITL 审批时长、工具超时率。
- 降级原则：观测/审计异常**绝不阻断主链路**（try/except 兜底）。

## 12. 模板的工具接入 / 循环上限 / 降级

### 12.1 工具接入（租户已注册且生效）
- `available_tools(ctx)`：从 `agent_tool` 取 **该租户 `enabled=true`** 的工具（`ToolDao.list_paged(tenant_id, enabled=True)`）。
- `load_tool_config(ctx, name)`：取该租户工具运行配置（`get_tool_config(name, tenant_id)`，仅 enabled 返回）。
- `call_tool(ctx, name, fallback=..., **kwargs)`：经 `PluginRegistry` 调用（超时/熔断由其包装），失败**降级**为 `fallback` 或结构化 `{"degraded": True}` 并审计。
- 工具来源唯一：**不读全局/其他租户**，只用 `ctx.tenant_id` 下已注册且生效的工具。

### 12.2 循环（最大次数）
- `max_iterations`（默认 8）：图内循环（如灰度多阶段、回滚重试）上限。
- `invoke_config(ctx)` 注入 `recursion_limit = max_iterations`，LangGraph 超限即中断。
- `loop_guard(state)`：节点内计数守卫，返回自增计数，超限抛错交由调用方降级（保底双保险）。

### 12.3 降级（失败不阻断）
- **工具失败**：`call_tool` 捕获异常 → 审计 → `fallback`（备用工具/规则）或结构化兜底。
- **观测/审计失败**：内部 try/except，绝不影响主链路。
- **模型/检索失败**：走兜底节点（规则回复/历史摘要/人工）。
- **HITL 超时**：`hitl_timeout_s` 超时置「拒绝/转人工」，不永久挂起。
- **循环超限**：`recursion_limit`/`loop_guard` 双保险，超限走降级出口。

## 13. db_review 需求细化（多方言 / 元数据前置 / 慢 SQL / 优化建议）

### 13.1 多数据库方言 + 目标库
- 支持方言：**MySQL / PostgreSQL**（可扩展 Oracle/SQLServer）。
- 输入：`db_type`、`target_database`（database/schema）、`target_tables`。
- **解析用 SQL parser 按方言**（如 sqlglot），不交给 LLM 解析；解析失败 → 降级「人工评审（HITL）」。

### 13.2 元数据前置查询（review 前**必须**）
评审前先经 `db_tool`（只读）取目标库元数据，注入 prompt：
- 表结构 DDL（MySQL `SHOW CREATE TABLE` / PG `pg_catalog`）
- 索引（`SHOW INDEX` / `pg_indexes`）
- 统计（表行数/大小/列基数）
- 约束/外键、（可选）当前负载/慢查询
- **脱敏**：表名/列名令牌化后给 LLM，原始元数据留工具层。
- 失败降级：返回「元数据不可用，置信度低」，必要时转 HITL。

### 13.3 SQL 分析
- **DDL**：是否 Online DDL、锁类型/时长、影响行数、索引重建、是否阻塞写入。
- **DML / 慢 SQL**：`EXPLAIN` 执行计划、全表扫描、索引命中、临时表/文件排序、深分页、隐式类型转换、`SELECT *`、N+1。
- 慢 SQL 判定：执行计划 + 统计（examined/returned）+ 规则阈值。

### 13.4 输出（含优化建议）
- `risk_level` + 维度结论（online_ddl/estimated_rows/lock_estimate_ms/core_path/cross_db/rollback_ready）
- `slow_sql`（is_slow、plan_summary、scan_type、rows_examined）
- `suggestions`：索引（缺失/冗余/复合顺序）、改写（去 `SELECT *`/分页/批量/避免函数包裹列）、DDL（Online 算法/分批/低峰）、回滚建议；**每条带依据**（元数据/规范引用）。
- `confidence` + `evidence`（溯源）。

### 13.5 Graph（元数据前置 + 并行预检 + 慢 SQL + 建议）
```
load_request → resolve_dialect(校验 db_type)
 → fetch_metadata(必须：DDL/索引/统计)          [db_tool 只读]
 → parse_sql(方言解析)
 → Send 并行预检：lock_estimate / rows_estimate / slow_sql_explain / spec_check(RAG) / history_incident(RAG) / index_analysis
 → fan-in → risk_grade(LLM 结构化) → suggestions(优化建议)
 → 条件：low→persist；med/high/crit→interrupt("change_approve")→approval→persist
```

### 13.6 工具扩展（db_tool，租户 enabled）
- `metadata.table_ddl` / `metadata.indexes` / `metadata.stats`（按 db_type 适配）
- `slow_sql.explain`（EXPLAIN / 执行计划）
- `index.analyze`（命中/缺失/冗余）
- 连接池按 `db_type + tenant` 隔离，**只读**。

### 13.7 提示词（前置元数据）
- `system`：角色=数据库变更评审专家；边界=只分析不执行；输出严格 JSON schema；安全=脱敏。
- `user`：方言 + 目标库 + SQL + **元数据摘要（DDL/索引/统计）** + 规范/事故引用 + 慢 SQL 执行计划。
- 明确要求：**先基于元数据判断可行性，再给风险/建议/依据**。

### 13.8 数据表扩展
- `agent_change_request` 加 `db_type`、`target_database`。
- `agent_change_review` 加 `metadata_snapshot(JSONB)`、`slow_sql_plan(JSONB)`、`suggestions(JSONB)`。
- 或新增 `agent_change_metadata`（元数据快照，便于审计/复现）。

### 13.9 多方言适配风险
- 不同库 `information_schema` 差异 → 工具层适配层；解析失败降级人工。
- 只读账号 + 从库；禁 sample rows；LLM 只收结构/统计。

## 14. db_review 输入与文件存储细则

### 14.1 输入二选一 + 长字符串校验
- **优先文件**（`.sql/.txt`）→ `get_object_bytes` 读取；无文件 → 用 `sql_text` 长字符串。
- 两者都缺 → `INIT_REQUIRED` 引导。
- **长度校验**：`sql_text` 设上限（建议 16KB，可配 `DB_REVIEW_SQL_MAX_BYTES`）；超限返回 `PARAM_ERROR`/`FILE_REQUIRED`，提示「内容过长，请上传 .sql 文件」。
- 前端：`textarea` 设 `maxLength` + 实时字数提示；超限禁用提交并提示上传。
- 与 token 预算联动：长 SQL 先校验阈值，避免进入 LLM 上下文。

### 14.2 文件路径：是否需要按会话 id 区分（结论：路径不需要，元数据需要）
**路径层不按 session_id 区分是合理的**：
- 文件是「租户/用户资源」，生命周期独立于会话，可跨会话/变更单复用、重提。
- `object_key` 唯一 + `agent_file` 版本化（`file_uuid`/`file_version`/`checksum`）已保证不覆盖、可追溯。
- 会话可删除，但文件不应随之消失（否则复现/审计丢失）。
- 同用户同月同名文件冲突已由 `file_uuid` 解决，无需 session 兜底。

**但必须在元数据层记录归属（关键）**：
- `agent_file` 增 `thread_id` / `request_id`（或新增关联表 `agent_change_file(file_id, request_id, thread_id, kind=script|drill)`）。
- 用途：按会话/变更单反查文件、会话删除时**可选**清理、审计追溯。

**何时才把 session 放路径**：仅当强要求「会话级物理隔离 / 随会话删除草稿」时用 `.../{thread_id}/`；代价是跨会话复用困难、路径变长、清理复杂。**默认不采用**。

### 14.3 最终路径（沿用现有 `build_object_key`）
```text
脚本：     db_review/t{tenant_id}/{yyyyMM}/{user_id}/script/{file_uuid}_v{version}.sql
回滚演练： db_review/t{tenant_id}/{yyyyMM}/{user_id}/drill/{file_uuid}_v{version}.pdf
```
- 顶层 `filetype=db_review`；`t{tenant_id}`、`yyyyMM` 与现有 `FileDao` 一致。
- `{file_uuid}_v{version}` 唯一防覆盖；原始名只存 `agent_file.original_name`。
- `script/`、`drill/` 区分类型；扩展名取真实 `file_ext`。
- 元数据走现有 `FileDao`（版本化/判重/checksum/bucket），不另起一套。

### 14.4 回滚演练记录（PDF）
- 上传 `.pdf` → `agent_file`（`kind=drill`、`request_id` 关联变更单）→ `pymupdf` 提取文本 → 校验「演练步骤/验证结果/结论/负责人」要素。
- 解析失败 → critical 风险转人工，不阻断主链路。
