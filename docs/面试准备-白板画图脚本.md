# 面试准备：白板画图脚本

> 配合《面试准备-项目介绍与题库》使用。每张图给：**画图顺序**（先画什么后画什么）、**口述话术**、**可能被追问**。

---

## 图 1：统一咨询分层（最常被要求画的图）

### 画图顺序（60 秒）

1. 顶部画一个小方框写「浏览器」，向下画一条箭头，标注 `POST /chat/stream (SSE)`；
2. 中间画一个**大一点的矩形**，标题「UnifiedGraph（薄图）」，里面横排四个小词：`路由 → 鉴权 → 分发 → 收尾`；
3. 大矩形下方向左、中、右各画一个方框：`qa`、`db_review`、`db_release`；
4. 在箭头旁标注 `thread_id = {会话}:{agent}:{轮次}`（这是关键，一定要写）；
5. 底部画一条横线，写 `PG / Redis / Milvus / MinIO / MQ`；
6. 最后在大矩形右侧补一个小标签：`事件映射`。

### 成品示意（照着抄）

```
        浏览器
          │  POST /chat/stream（SSE）
          ▼
┌──────────────────────────────────────────────┐
│  UnifiedGraph（薄图）                         │
│  路由 → 鉴权 → 入口校验 → 分发 → 写turn/收尾    │
│  事件映射: token/progress/meta/interrupt/card │
└──────────────────────────────────────────────┘
   │ thread_id = {会话U}:{agent}:{turn}
   ├──────────────┬──────────────┬──────────────┐
   ▼              ▼              ▼
┌────────┐  ┌────────────┐  ┌──────────────┐
│  qa    │  │ db_review  │  │ db_release   │
│ 检索   │  │ 4路预检    │  │ 沙箱执行     │
│ →精排  │  │ →分级      │  │ →验证        │
│ →生成  │  │ →建议      │  │ →放行        │
│ →记忆  │  │ →审批⏸     │  │ →输出SQL     │
└────────┘  └────────────┘  └──────────────┘
   │              │              │
   └──────────────┴──────────────┘
                  ▼
        PG / Redis / Milvus / MinIO / MQ
```

### 口述话术（30 秒）

> 「上面是一个薄图，只做路由、鉴权、入口校验和事件映射，不含业务节点；下面是三张独立编译的图，各自有自己的 State。父图和子图用不同的 thread_id 做 checkpoint 分区，子图是运行时通过适配器调用的，不是 LangGraph 原生的嵌套子图。」

### 可能被追问

| 追问 | 回答要点 |
|---|---|
| 为什么叫「薄图」？ | 只做横切关注点（路由/鉴权/事件/落库），业务节点全在子图，避免 State 膨胀与 `if agent_type ==` |
| 为什么不用原生 subgraph？ | Agent 是租户级动态注册（DB 决定），编译期无法固定节点；且 HITL 恢复走 `checkpoint_ns` 更复杂 |
| 事件映射在哪做？ | 适配器里过滤子图的 `astream_events`，只上抛 token/progress/meta，父图零感知子图细节 |
| 路由怎么做的？ | 显式（卡片/模板跳过分类）→ 隐式（规则关键词）→ 未命中交 LLM → 兜底 qa |

## 图 2：RAG 完整链路（第二常问）

### 画图顺序（50 秒）

1. 从左到右画一条主线：`query → 查询分类 → 检索 → 精排 → 判分 → 生成`；
2. 在「查询分类」下方挂两个分支：`多查询改写（BROAD）`、`HyDE（VAGUE）`；
3. 在「判分」下方画一个菱形，两条箭头发散：`≥0.45 → RAG 生成（带 sources）`、`<0.45 → 直答/联网兜底`；
4. 在「生成」后面补一个节点：`save_memory（摘要/长期记忆）`；
5. 底部单独画一行「离线链路」：`文档 → 解析(OCR) → 父子片 → 子片向量化 → Milvus`。

### 成品示意

```
在线
query ──▶ 查询分类 ──▶ 混合检索 ──▶ 精排 ──▶ 判分(首条分数)
            │           dense+sparse   bge-      │
            │           RRF 融合        reranker  │
            │                                     ├─ ≥0.45 ─▶ RAG 生成（附 sources）
            ├─ 多查询改写（BROAD）                 │
            └─ HyDE（VAGUE）                      └─ <0.45 ─▶ 直答 / 联网兜底
                                                              │
                                                              ▼
                                                      save_memory（摘要+长期记忆）

离线
文档 ──▶ 解析（PDF/Word/扫描件 OCR）──▶ 父子片切分 ──▶ 子片向量化(BGE-M3) ──▶ Milvus
                                          └ 父片全文冗余在子片行（命中后回填）
```

### 口述话术（30 秒）

> 「检索用 hybrid：dense 抓语义、sparse 抓专有名词和 SQL 关键字，RRF 融合后取 top20 候选，再用 cross-encoder 精排取前 5。置信度就取首条精排分数，0.45 以上走 RAG，否则直答或联网兜底。文档侧是父子片，子片进向量库，命中后回填父片给模型。」

### 可能被追问

| 追问 | 回答要点 |
|---|---|
| RRF 分数量纲？ | `Σ1/(k+rank)`，0.0x 量级，**只能排序不能当相似度**（我踩过：直接当置信度导致永远低分） |
| 精排为什么必要？ | 向量相似度区分不了"命中但答非所问"，cross-encoder 精度高但要先粗排缩小候选 |
| 0.45 怎么来的？ | 初版 0.75 发现 reranker 分数分布 0.2~0.6 永远达不到，按日志分布下调 |
| 没召回怎么办？ | 看 `rag.retrieve.empty` 的 tenant/recall_k，再查 parse_status、Milvus 分区、embedding 一致性 |
| 父子片好处？ | 小片召回准、大片上下文全，避免"召回对了但上下文不够" |

## 图 3：HITL 审批时序（最容易被要求画）

### 画图顺序（50 秒）

1. 画四条竖线（泳道）：`用户/前端`、`后端 API`、`Agent 图`、`PostgreSQL`；
2. 从「前端」画箭头到「后端」：`POST /chat/stream`；
3. 「后端」→「图」：`ainvoke/astream`；
4. 「图」内部标 `approve 节点 → interrupt()`，箭头指向「PG」写 `checkpoint`；
5. 「图」→「后端」回 `interrupt 事件`，后端 → 前端：`SSE: interrupt`（前端弹框）；
6. 前端 → 后端：`POST /resume {approved}`；后端 → 图：`Command(resume)`；
7. 图继续：`save_memory → persist`，同时把「审批前段统计」从 state 取出；
8. 图 → 后端 → 前端：`token 流` + 最后 `result_card`（合并两段耗时/token）。

### 成品示意

```
前端            后端API            Agent图              PG
 │  POST /chat/stream │                 │                │
 │───────────────────▶│  astream        │                │
 │                    │────────────────▶│                │
 │                    │                 │ approve 节点    │
 │                    │                 │ interrupt() ⏸  │
 │                    │                 │───────────────▶│ checkpoint
 │                    │◀── interrupt ───│                │
 │◀── SSE interrupt ──│                 │                │
 │  （弹审批框，此时不展示耗时/token）    │                │
 │  POST /resume      │                 │                │
 │───────────────────▶│ Command(resume) │                │
 │                    │────────────────▶│ 继续执行        │
 │                    │                 │ save_memory     │
 │                    │                 │ persist ───────▶│ turn/变更单
 │◀── token 流 ───────│◀── token ───────│                │
 │◀── result_card ────│  （耗时/token = 前段(state) + 后段）│
```

### 口述话术（30 秒）

> 「审批用的 interrupt：节点里挂起，现场存 checkpoint。前端收到 interrupt 帧弹框；用户点通过后走 resume，用 Command 恢复，**同一条消息继续流式输出**。审批前的耗时和 token 先写进图状态不展示，最终卡片把前后两段合并，等待时间不计。」

### 可能被追问

| 追问 | 回答要点 |
|---|---|
| 挂起时服务重启会丢吗？ | 不会，状态在 PG 的 checkpoints，resume 靠 thread_id + ns 恢复 |
| thread_id 用哪个？ | 子图分区 `{会话}:{agent}:{轮次}`，resume 必须用同一个 |
| 为什么等待时间不计？ | 人工时间不该算进系统耗时，否则指标失真 |
| 统计怎么合并？ | 审批前 `aupdate_state` 写 `gate_token_usage/gate_latency_ms`，resume 时读出相加 |
| 清会话会影响审批吗？ | 会——所以删会话只删 `agent_thread`，不动 checkpoint |

## 图 4（加分）：多租户隔离四层

### 画图顺序（30 秒）

画四行横条，每行左侧写组件，右侧写隔离手段：

```
PG       每张业务表带 tenant_id，DAO 强制过滤
Milvus   tenant_id 作分区键，检索 expr 过滤
Redis    key 前缀 t:{tenant}:u:{user}:...
MinIO    对象键按租户前缀
   ▲
   全部来自 JWT 里的 tenant_id（不信任请求头）
```

**口述**：「隔离不是靠一处，而是存储四层都带租户维度，且身份只信 JWT。我们踩过子图入口漏传 tenant_id 导致检索按租户 0 过滤的坑。」

## 画图通用技巧

1. **先画主干再补细节**：先一条线走完，再加分支和标注；
2. **每个箭头必须有标签**（协议名 / thread_id / 条件），否则等于没画；
3. **主动标注取舍**：在图的角落写「为什么不用 X」，面试官会觉得你想过；
4. **数字要具体**：top20 候选、精排前 5、阈值 0.45、6 轮摘要、TTL 1 天；
5. 画错了别擦，直接说「这里我调整一下」，比反复涂改自然。
