# 统一咨询入口设计方案

> 现行实现基线（2026-11-16）。业务为三个 Agent：知识问答 `qa`、变更评审 `db_review`、变更发布 `db_release`。
> 代码位置：`backend/orchestration/`（编排）、`backend/agents/*`（业务图）、`backend/api/v1/tenant/agent/unified_*.py`（接口）、`dashboard/src/pages/unified/`（前端）。

---

## 1. 目标与范围

- **一个入口**：用户只面对一个聊天框，所有 Agent 的「发起」动作收敛到 `POST /unified/chat/stream`；
- **能力由后端下发**：卡片、模板、入口字段、进度标签全部来自 `AgentSpec`，前端不写死 Agent；
- **保留各图独立**：每个 Agent 独立编译、独立 State、独立演进，编排层不写 `if agent_type == ...`；
- **人工在环**：评审 / 发布在关键节点 `interrupt()` 挂起，前端弹框审批后续跑。

**范围外**：平台不执行生产 SQL（发布只做影子库验证并输出最终 SQL）。

---

## 2. 分层架构

```
浏览器（React + antd）
  │  POST /unified/chat/stream（SSE）
  ▼
统一编排层 UnifiedGraph（薄图）
  ├─ 路由：显式通道（卡片/模板）· 隐式通道（规则分类，未命中问 LLM）
  ├─ 鉴权：入口 scope（unified:ask）+ 租户开通（agent.enabled）+ spec.scope
  ├─ 分派：AgentAdapter（stream / dispatch / pipeline）
  ├─ 事件映射：token / reasoning / progress / meta / interrupt / result_card / error
  └─ 收尾：写 turn、meta 帧、done
  ▼
Agent 图（各自编译、独立 State）
  ├─ qa        classify → [hyde|multi_query] → retrieve → grade → generate_* → enqueue_pending → save_memory
  ├─ db_review load → fetch(4 路并行) → aggregate → grade → suggest → approve(interrupt) → save_memory → persist
  └─ db_release load_request → guard → shadow_execute → verify → gate(interrupt) → save_memory → persist
  ▼
Orchestrator + AgentRegistry（自动注册 + DB 覆盖 display_name/description）
  ▼
PostgreSQL · Redis · Milvus · MinIO · RabbitMQ
```

**子图不是原生嵌套**：编排层用 `thread_id = {会话U}:{agent_type}:{turn_id}` 给子图做 checkpoint 分区，运行期通过 adapter 调用子图，事件由 adapter 过滤后上抛。

---

## 3. 路由

| 通道 | 触发 | 规则 |
|---|---|---|
| 显式 | 点能力卡片 / 模板问题 / 带 `agent_type` | 跳过分类，直接分派 |
| 隐式 | 自由输入 | 规则分类（关键词 → qa / db_review / db_release）→ 未命中交 LLM 分类 → 仍失败兜底 `qa`（`default_agent=True`） |

路由结果通过首个 SSE 帧 `routing_decision` 返回（含 `agent_type`、`thread_id`）。

---

## 4. SSE 事件协议

| 事件 | 触发时机 | 关键字段 |
|---|---|---|
| `routing_decision` | 路由完成 | `agent_type` / `thread_id` |
| `token` | 正文增量 | `content` |
| `reasoning` | 思考模式下的推理增量 | `content` |
| `progress` | 阶段进度（来自 `spec.progress_labels`） | `stage` |
| `meta` | 问答收尾 | `answer_mode` / `confidence` / `sources` / `latency_ms` / `token_usage` |
| `interrupt` | HITL 挂起 | `gate`（`change_approve` / `gate_approve`）/ `request_id` / `risk_level` / `answer` |
| `result_card` | 卡片结果 | `risk_level` / `status` / `final_sql` / `answer` / `suggestions` / `latency_ms` / `token_usage` |
| `orchestration_result` | 并行编排（纪律见 §9） | `result.parallel.{qa,db_review}` |
| `error` | 失败 | `code`（业务码优先）/ `message` |
| `stopped` / `done` | 用户停止 / 正常结束 | — |

**错误不降级**：关键写库（turn / 评测 / 记忆 / outbox）失败直接抛出，`error` 帧携带真实 `code` 与 `msg`，前端用红底卡片展示。

---

## 5. HITL（人工审批）

```
提交 → 图执行 → interrupt(gate) ──▶ 前端弹审批框（此时不展示耗时/token）
                                        │
                        通过/驳回 ──▶ POST /unified/chat/resume
                                        │  Command(resume)
                                        ▼
                              同一消息继续流式 → result_card（耗时/token 合并前后两段）
```

- 前端通过 `interrupt` 帧拿到 `gate` 与 `request_id`，审批请求体 `{thread_id, agent_type, approved, comment}`；
- 审批前段统计写入图状态（`gate_token_usage` / `gate_latency_ms`），resume 完成后与后段合并输出；
- 审批等待时间**不计入**耗时。

## 6. 会话与记忆

| 层 | 存储 | 说明 |
|---|---|---|
| 会话条目 | `agent_thread` | 首轮自动命名（仅改一次）；删除只删该行 |
| 轮次历史 | `agent_unified_turn` | **唯一真相源**；`turn_index` 由 `max+1` 计算，唯一索引 `(thread_id, turn_index)` |
| 图状态 | `checkpoints` 等 | 父图按会话、子图按 `{U}:{agent}:{turn}` 分区 |
| 短期记忆 | Redis | `t:{tenant}:u:{user}:session:{thread}`，TTL 1 天，`ltrim` 保留最近 N 条 |
| 长期记忆 | `agent_long_term_memory` | `block=summary/fact/preference`；qa 每 6 轮摘要触发，评审/发布在审批或放行后写入 |

`turn.payload` 结构：

```json
{
  "execution_mode": "stream",
  "source": "implicit",
  "answer_mode": "rag",
  "confidence": 0.62,
  "sources": ["xxx.pdf > 第 3 页"],
  "retrieved_contexts": [
    {"doc_id": "...", "chunk_id": "...", "content": "...", "page": 3, "score": 0.6213, "source": "..."}
  ]
}
```

`latency_ms` / `token_usage` 独立列存储；模型不返回 usage 时按字符估算并标 `estimated`（前端显示 `≈`）。

## 7. 知识问答（qa）关键实现

- **检索**：Milvus 混合检索（dense + sparse，RRF 融合）→ bge-reranker 精排（`top_k=全部候选`）→ 取前 `final_k`；
- **置信度**：取首条精排分数（0~1），`>= QA_HIGH_CONFIDENCE_THRESHOLD`（默认 0.45）判定高置信；
- **降级语义**：精排不可用时分数是 RRF 0.0x（只排序），`confidence` 置 1.0 并标记 `_rerank_used=False`；
- **生成**：`generate_rag`（有上下文）/ `generate_direct`（低置信直答）/ `generate_general`（闲聊）；
- **查询改写**：BROAD 走多查询改写、VAGUE 走 HyDE（均为一次 LLM）；
- **待补充队列**：低置信入 `agent_knowledge_pending_queue`（写库失败即报错）；
- **OCR**：扫描件按页降级识别（RapidOCR 启动预加载）。

---

## 8. 扩展一个新 Agent

1. 新建 `backend/agents/<name>/{agent.py, state.py, nodes.py, prompts.py}`；
2. 继承 `Agent` 并实现 `metadata() -> AgentSpec`（`agent_type / display_name / description / scope / entry_fields / card / execution_mode / generate_nodes / progress_labels / long_term_blocks / tags`）；
3. 在 `agent.py` 内 `build_graph()` 返回编译后的图；
4. 前端无需改动：卡片、模板、入口表单、事件渲染均按 `AgentSpec` 与 `event_type` 驱动；
5. 若需 HITL：在节点内 `interrupt()`，并确保 `execution_mode` 走 `stream`。

---

## 9. 约束与已知取舍

- **不原生嵌套子图**：换取动态（租户级注册）、HITL 恢复简单、事件集中过滤；代价是 checkpoint 分区而非命名空间嵌套；
- **并行编排**（`orchestration_result`）仅用于"qa 规范 + db_review 评审"这类无 HITL 的组合，审批类不放并行；
- **思考模式**依赖模型支持（网关忽略 `thinking` 参数时无 `reasoning` 帧）；
- **token 统计**优先真实 usage，缺失时估算（`≈`），不作为计费依据。
