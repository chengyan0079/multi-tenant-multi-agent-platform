## 1. 范围与架构

### 1.1 收口边界（本版核心）

统一入口是一个**流式聊天框**：空态展示 4 张 Agent 卡片 + 若干模板问题；点击卡片即进入该 Agent 的入口逻辑。收口的仅是「**发起 Agent 图执行**」这一个动作。

| 类别 | 端点/页面 | 处置 |
| --- | --- | --- |
| **执行入口（收口）** | QA `chat`/`chat/stream`/`chat/stop`；QA 会话 CRUD；面试 `POST /sessions`、`chat`、`chat/stream`、`chat/stop`；`POST /exam/submit`；`POST /resume/upload` | 删除，统一由 `/unified/chat/stream` 发起（§8.2） |
| **查看/管理（D6 保持不变）** | `/qa/results/*`、`/qa/files/*`、面试结果列表/详情/报告/删除、`/exam/my-submissions*`、教师复核 `/submissions/{id}/review` 与 `/confirm`、`/resume/reviews*` | 保留，URL 与响应字段不变（§8.3） |
| **执行链（内部保留）** | 4 张图、`Orchestrator`、`AgentRegistry`、Outbox/broker handler、exam `interrupt()` HITL、resume 超时扫描、RAGAS | 全部保留，仅入口改由 adapter 调用（§8.4） |

**交互形态分两类，但都从唯一入口进入**：

| 形态 | Agent | 输入 | SSE 事件 |
| --- | --- | --- | --- |
| 对话型 | qa / interview | 文本（面试含入口表单） | `token` 逐字 + `progress` / `meta` |
| 任务型 | exam / resume | 文件 + 表单字段 | `task_started` / `task_progress` / `task_result`；exam 另有 `review_required` |

> 「流式」指统一 SSE 通道；对话型流 token，任务型流状态事件。两者共用同一套帧协议（§8.5）。

### 1.2 目标

1. 用户只面对一个入口，4 个 Agent 的发起动作全部收敛。
2. 会话、历史、记忆**一次维护**：一个写入逻辑、一个历史源、一份会话级摘要。
3. 观测**一次**：一条 trace 覆盖意图分类与所有下游调用（含异步任务），`trace_id` 贯穿日志与数据。
4. 统一咨询持有**会话级 checkpoint**（`thread_id = U`）。
5. 4 张图保持独立编译、独立 State、独立演进。
6. **增减子 Agent 改动量最小**（D10）：不动编排层、协议、会话与观测、前端。
7. **数据层零冲突**（D14）：全库只有一套会话 id 体系，业务表无会话语义字段。

### 1.3 架构选型：统一编排层 + 独立执行图

| 判断依据 | 证据 |
| --- | --- |
| 4 个 State 字段完全不同（QA 检索/精排/`answer_mode`；面试 `current_stage/question_bank/report`；exam 逐题 + HITL；resume 六维评分） | `agents/qa/state.py:39-72`、`agents/interview/state.py:55-90` |
| 生命周期异构：QA/面试同步多轮，exam/resume 走 Outbox 异步，exam `interrupt()` 可挂起数天 | `exam.py:150`、`resume.py:135`、`exam/nodes.py:824` |
| resume 图不绑 checkpointer | `agents/resume/graph.py:46` |
| 已有 `AgentRegistry` + `Orchestrator.run_agent` 统一调度 | `server/managers/orchestrator_manager.py:19-24`、`orchestration/orchestrator.py:25-56` |

**收口做在接入层与平台层，执行层保持隔离**：各图 State 与生命周期彼此独立，统一层只负责意图路由、会话与观测，通过 adapter 调用独立编译的图。

### 1.4 设计原则

| # | 原则 | 落地手段 |
| --- | --- | --- |
| P1 | 声明优于分支 | 编排层不写 `if agent_type == 'qa'`，所有差异由 `AgentSpec` 声明（§3） |
| P2 | 单一真相源 | 意图提示词、scope、卡片、菜单、SSE 标签、checkpoint 分区、观测 tags 全部由 spec 生成（§3.3） |
| P3 | 复用优先 | 沿用 `OrchestratorManager` 注册循环与 `AgentRegistry.load_from_db()` 读库（§3.1、§3.4） |
| P4 | 协议稳定 | SSE 帧结构、turn 表结构不随 Agent 增减变化；扩展走 `event_type` + `payload` |
| P5 | 平台能力不感知业务 | 会话服务、观测、鉴权、前端卡片注册表都不 import 任何 `agents/*` |
| P6 | 失败早暴露 | spec 启动期 fail-fast 校验（§3.5），遵循项目「启动 manager 必须 fail-fast」约定 |
| P7 | 前后端解耦 | 后端下发 `route_key` 与卡片配置；前端按 `event_type` 查渲染器表 |
| P8 | 会话语义唯一 | 业务表不存 `session_id` / `thread_id` / 会话态 `status` / 摘要（§5.4） |

### 1.5 非目标

- 教师复核端点 `POST /exam/submissions/{id}/confirm` 本期保持独立，不在统一卡片内完成（§4.6）。
- 旧数据兼容与迁移（D5）。
- LangGraph subgraph；4 张图的 State 结构与编译方式不变。
- 提示词一期不接 Nacos，配置中心仅在 §3.11 定义的二期路径中引入。

## 2. 分层架构与数据流

### 2.1 总览

```
┌───────────────────────────────────────────────────────────────────┐
│ 接入层   /api/v1/tenant/unified/*                                  │
│   chat/stream(SSE) · attachments(multipart) · sessions · agents     │
│   token · require_tenant · require_scope · 停止 · 输入护栏           │
├───────────────────────────────────────────────────────────────────┤
│ 统一编排层  UnifiedGraph（薄图, checkpoint=U）+ 双通道路由 + 分发    │
├───────────────────────────────────────────────────────────────────┤
│ 注册表    AgentRegistry（复用）→ specs()：卡片/提示词/scope/菜单     │
├───────────────────────────────────────────────────────────────────┤
│ 会话记忆层  UnifiedConversationService                              │
│   agent_thread(U) + agent_unified_turn(turn_id) + existing_summary   │
├───────────────────────────────────────────────────────────────────┤
│ 观测层    ApiLogMiddleware + Langfuse 5.x + trace_id                 │
├───────────────────────────────────────────────────────────────────┤
│ 执行层    4 张独立编译的图 + Orchestrator + adapter                  │
├───────────────────────────────────────────────────────────────────┤
│ 异步层    Outbox → MQ → broker handler → HITL interrupt              │
└───────────────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 不负责 | 新增 Agent 是否要改 |
| --- | --- | --- | --- |
| 接入层 | 协议、鉴权、SSE 帧、附件、停止 | 业务判定、落库 | ❌ |
| 统一编排层 | 双通道路由、上下文组装、观测挂载 | 各 Agent 内部状态机 | ❌ |
| 注册表 | 读库合并 spec、校验、生成派生物 | 执行图 | ✅ 仅注册循环加一行 |
| 会话记忆层 | 会话元信息、历史正文、摘要 | 图执行态 | ❌ |
| 观测层 | 一次挂 callbacks、trace 贯穿 | 业务字段 | ❌ |
| 执行层 | 各业务 State 与节点 | 会话归属、历史回放、审计 | ✅ 仅新增图包 |
| 前端 | 通用聊天壳 + 卡片/事件渲染器表 | 硬编码 Agent 清单 | ❌ |

### 2.2 一次请求的完整数据流

```
POST /unified/chat/stream  { session_id, agent_type?, message, entry_values, attachments, ... }
  │
  ├─ ① 静态鉴权：get_current_user → require_tenant → require_scope(unified:ask) → check_input
  │      失败 → 401/403，不建立 SSE
  ├─ ② U = ThreadDao.get_or_create(session_key=S)                     〔R1 必修〕
  ├─ ③ turn_id = 预分配 UUID（本轮唯一标识，业务表与事件共用）
  ├─ ④ 路由：显式 agent_type → 跳过分类；否则规则前置 → LLM 分类
  ├─ ⑤ 运行期动态鉴权（spec.scope + is_enabled_for_tenant）
  │      失败 → 写 status='failed' turn + SSE error+done，不调子图
  ├─ ⑥ UnifiedGraph.ainvoke(cfg_U) → routing 写入 U checkpoint（含本轮 HumanMessage）
  ├─ ⑦ SSE routing_decision → adapter 按 execution_mode 执行
  │      对话型：astream_events → progress / token / meta
  │      任务型：attachment_service 建业务行 + enqueue_task → task_started / task_progress
  ├─ ⑧ UnifiedConversationService.append_turn()
  │      一次写：turn 行（含 payload.artifact_*）+ 业务明细 + touch(U) + checkpoint 写回
  └─ ⑨ SSE done；ApiLogMiddleware 落调用日志；Langfuse 异步导出
```

### 3.2 `AgentSpec` 字段

新增**一个**纯数据模块 `backend/orchestration/agent_spec.py`（只放 dataclass 与 merge/validate，不 import 任何 `agents/*`，避免循环依赖）；各 Agent 的默认 spec 写在自身 `agent.py` 的 `metadata()` 中。

```python
@dataclass(frozen=True)
class AgentSpec:
    # 身份（可被 agent 表覆写）
    agent_type: str
    display_name: str
    description: str
    version: str = "1.0.0"

    # 意图识别
    intent_labels: tuple[str, ...] = ()
    intent_examples: tuple[str, ...] = ()
    intent_hint: str = ""
    default_agent: bool = False          # 全局恰有一个，隐式通道异常时兜底

    # 权限
    resource: str = ""
    scope: str = ""                      # 如 unified:ask / exam:upload
    menu_scope: str = ""

    # 卡片与入口（v3.0）
    card: AgentCard | None = None            # 卡片展示（§5.11）
    templates: tuple[str, ...] = ()          # 模板问题，点击=带 agent_type 自动发送
    entry_fields: tuple[EntryField, ...] = ()  # 入口表单字段（§5.11），用于生成动态 Pydantic 校验模型
    accept_files: tuple[str, ...] = ()       # 需要的文件类型：( ".docx", ) / ( ".pdf", )

    # 执行
    execution_mode: Literal["stream", "task", "clarify", "pipeline"] = "stream"
    adapter: str | None = None
    checkpoint_scope: bool = True           # True=按业务实例固定分区；False=每轮独立分区
    progress_labels: tuple[ProgressLabel, ...] = ()  # 节点名→文案，具体对象（§5.11）
    generate_nodes: tuple[str, ...] = ()
    done_fields: tuple[str, ...] = ()
    init_prompt: str = ""

    # 交互
    guidance_message: str = ""
    guidance_action_label: str = ""
    route_key: str = ""
    pipeline_steps: tuple[PipelineStep, ...] = ()  # 多 Agent 串联步骤（§4.9）

    # 菜单 / 观测 / 记忆
    menu: MenuSpec | None = None
    tags: tuple[str, ...] = ()
    trace_name: str = ""
    summary_policy: str = "default"
    short_term_limit: int = 20              # 短期窗口读取条数（§5.8）
    long_term_blocks: tuple[str, ...] = ("summary", "fact", "preference")  # 长期记忆块类型（§5.8）
```

`AgentMeta` 扩展与合并点：

### 3.3 从 spec 生成的派生物

`_rebuild_derived()` 在每次 `load_from_db()` 末尾原子重建，结果挂在 `AgentRegistry` 实例上，编排层只读：

| 派生物 | 生成方式 |
| --- | --- |
| 路由提示词 | 遍历 `specs()` 拼「label → display_name + description + intent_hint + examples」；`clarify`/`multi_agent` 为编排层内建 label |
| label → agent 映射 | `{label: spec.agent_type for spec in specs() for label in spec.intent_labels}` |
| 卡片配置 | `GET /unified/agents` 输出 `spec.card` + `templates` + `entry_fields` + `accept_files` 的公开子集 |
| 动态入口校验模型 | 按每条 `spec.entry_fields` 用 `pydantic.create_model()` 生成 `EntryValues_<agent_type>`，缓存于 `AgentRegistry`；请求到达时由编排层 `model_validate()`（§5.11） |
| scope 映射 | `SCOPE_BY_AGENT = {s.agent_type: s.scope}`；`scope_for_agent()` 保持「未登记即拒绝」 |
| guidance / pipeline 文案 | `spec.guidance_message` / `spec.pipeline_steps` |
| 进度与 token 过滤 | `spec.progress_labels` / `spec.generate_nodes` |
| 菜单 | `spec.menu` → 幂等同步 `agent_menu`（§10.4） |
| checkpoint 分区 | `spec.checkpoint_scope` 决定子图是否挂独立 checkpoint（§4.8） |
| 观测 tags / trace_name | `spec.tags` / `spec.trace_name` |

> 内建 label 映射：`clarify` → `execution_mode='clarify'`（产出 `guidance` 事件追问）；`multi_agent` → `execution_mode='pipeline'`（**先出 `pipeline_plan`，再真跑串联**，见 §4.9）。二者不对应具体 Agent，不参与 `scope_for_agent()`。
> `entry_fields` 在 `_rebuild_derived()` 中按 spec 生成对应的 Pydantic 校验模型（§3.3、§5.11），运行时对 `EntryPayload` 做二次业务校验；新增 Agent 不改统一层。

### 3.7 Adapter 协议与扩展等级

```python
class AgentAdapter(Protocol):
    def to_subgraph_input(self, unified_state, spec, entry_values, attachments) -> dict: ...
    def from_subgraph_output(self, result, spec) -> AgentOutcome: ...
    async def stream(self, graph, initial_state, config) -> AsyncIterator[dict]: ...
    async def on_first_turn(self, spec, turn_id, entry_values, attachments) -> dict: ...
    def normalize_events(self, event, spec) -> dict | None: ...
```

| 等级 | 场景 | 需要写什么 | 改动量 |
| --- | --- | --- | --- |
| L0 | 改文案 / 展示名 / 开关 / 模板问题 | 管理端改 `agent` 表或 spec 默认值 | 0 |
| L1 | 新增普通流式 Agent | 图包（`metadata()` 返回 spec）+ 注册循环一行 + `Scope` 常量 + `agent` 表一行 | 2 个新文件 + 2 行 + 1 行数据 |
| L2 | 需特殊初始化 / 自定义 done 字段（面试类） | L1 + 一个 adapter | L1 + 1 |
| L3 | 任务型 / HITL（exam、resume） | L2 + `attachment_service` 接入 + broker handler 关联 | L2 + 队列配置 |

任何等级都**不改**：`unified_chat.py`、`unified_graph.py`、`UnifiedConversationService`、`tracing.py`、turn 表、SSE 协议、`config_refresh.py`、管理端 CRUD、前端。

### 3.9 Agent 下线（软删除）

Agent 下线只改状态，不做任何物理删除（D19）：

| 项 | 做法 |
| --- | --- |
| 操作入口 | `PATCH /admin/agents/{type}/enabled=false`（`admin/agents.py:108-147`），写 `agent.enabled` 并 `publish_config_refresh("agent_registry")` |
| 生效链 | `refresh()` → `load_from_db()` → `_rebuild_derived()`：路由候选移除、提示词不含、卡片不含、菜单 `visible=false`；5s 跨副本生效 |
| 图包 / 注册行 / `agent` 目录行 | **一律保留**；`enabled=false` 的 spec 仍在 `list_types(only_enabled=False)` 中，供管理端恢复 |
| 历史数据 | turn 行、业务表行、checkpoint 分区全部保留可查；不清理、不迁移 |
| 恢复 | `PATCH ... enabled=true` 即恢复，无需改代码、无需数据回填 |
| 租户级下线 | `PUT /admin/agents/tenants/{id}/capabilities` 置 `enabled=false`，仅影响该租户 |

**管理端 `DELETE /admin/agents/{type}` 端点本期不调用**；由于无物理删除，模型绑定解绑、注册循环改动、重启（V8 全量校验）均不再与下线动作关联。

约定：

- 模板变量一律用 `str.format()` 具名占位（如 `{capabilities}`），不做 `eval` / f-string 拼接用户输入；用户输入经 `check_input()` 后进入。
- `render_route_prompt(specs)` 把 `ROUTE_SYSTEM_PROMPT` 与动态生成的 label/description/examples 段落拼装；动态部分由 spec 提供，常量只定义"怎么说"。
- **二期 Nacos 路径**（不在本期实施）：新增 `ConfigGroup.PROMPT` 下的 `data_id`（如 `unified.route.system`、`unified.summary.compress`），用 `get_prompt(data_id)`（`prompts_cache.py:20`，Redis 缓存 1h）读取，`warmup_prompts()` 启动预热、`refresh_prompt()` 配置变更后刷新；**常量降级为配置缺失/读取失败时的 fallback**，保证零配置可启动。二期只需替换 `backend/prompts/unified.py` 内部取值实现，调用方零改动。

## 4. 统一编排层设计

### 4.1 薄图 `UnifiedGraph` 与 `UnifiedState`

唯一持有**会话级 checkpoint** 的图：`builder.compile(checkpointer=app_state.checkpointer)`，`thread_id = U`（`agent_thread.id`）。

```
START → load_context → route → authorize → dispatch_decision → END
```

| 节点 | 职责 |
| --- | --- |
| `load_context` | 取 `messages` 窗口 + `existing_summary`，组装本轮上下文 |
| `route` | 显式通道直通 / 规则前置 / LLM 结构化分类（提示词由 spec 生成） |
| `authorize` | `scope_for_agent()` + `has_scope()` + `is_enabled_for_tenant()` |
| `dispatch_decision` | 只出 `agent_type` / `execution_mode` / 入口字段校验结果 |

```python
class UnifiedState(TypedDict, total=False):
    messages: Annotated[list[BaseMessage], add_messages]  # 运行时上下文窗口
    existing_summary: Optional[str]        # 会话内滚动摘要（checkpoint）
    routing: RoutingDecision              # 具体对象，见 §5.11
    entry: EntryPayload | None            # 入口字段具体对象，见 §5.11
    short_term: list[ShortTermTurn]       # Redis 短期窗口，见 §5.8
    long_term: list[LongTermMemoryBlock]  # PG 长期记忆，见 §5.8
    turn_index: int
    last_agent_type: str
    tenant_id: int; user_id: int; session_id: str; thread_id: str
```

`UnifiedState` 不承载任何业务域字段，也不含任何 `dict` 属性；全部结构化字段为 Pydantic `BaseModel`（§5.11）。LangGraph checkpoint 序列化边界由 `JsonPlusSerializer` 处理 BaseModel，读取时在 `load_context` 用 `model_validate()` 复原（P0 验证，见 §12 R19）。面试状态机 `current_stage/question_bank/report` 由面试图自己的 checkpoint 跨轮保存（§4.8）。

### 4.2 流式输出与 checkpoint 写回

1. `state = await unified_graph.ainvoke({...HumanMessage...}, config=cfg_U)` → 得 `routing`，checkpoint 持久化本轮用户消息。
2. `event_generator` 推 `routing_decision`；`adapter.stream()` 用 `astream_events(..., version="v2")` 驱动对话型子图，`normalize_events()` 按 `spec.progress_labels` / `spec.generate_nodes` 产出 `progress` / `token`；任务型由 adapter 产出 `task_*` 事件。
3. `UnifiedConversationService.append_turn()` **一次写回**：turn 行 + 业务明细 + `touch(U)` + checkpoint 中的 assistant 消息与 `existing_summary`。

> 写回首选 `unified_graph.aupdate_state(cfg_U, values)`；**该 API 在 langgraph 1.0.9 的签名与行为须在 P0 用真实环境验证**（§12 R5）。若不可用，退化为「薄图再 `ainvoke` 一次仅走 persist 分支」，并保证 `route` 幂等不重复分类。

### 4.3 双通道路由（D13）

| 通道 | 触发 | 处理 | Token |
| --- | --- | --- | --- |
| **A 显式** | 点 Agent 卡片 / 点模板问题 | 请求带 `agent_type` → **跳过意图分类** → 直接 `authorize` + `dispatch` | 0 |
| **B 隐式** | 直接在输入框打字 | 规则前置 → LLM 结构化分类 → 路由 | 1 次分类 |

- 规则前置：问候 / 感谢 / 道别 / 身份 / 能力 5 类，命中直接模板回复、零 Token；「身份/能力」回复由 `specs()` 动态拼装。
- LLM 分类用本项目签名：`llm = await get_structured_llm("unified", IntentResponse)`（`IntentResponse` 为 `BaseModel`，§5.11）；`await llm.ainvoke([SystemMessage(content=render_route_prompt(specs_snapshot)), HumanMessage(content=render_turn_input(...))])`，其中 `render_route_prompt()` 使用 `ROUTE_SYSTEM_PROMPT` + spec 动态段落（§3.11），`render_turn_input()` 使用 `ROUTE_TURN_TEMPLATE`（§3.11）；`llm_factory.py:277-378` 收 `messages: list`。`get_llm("unified")` 无绑定时回退 `ModelDao.get_active("llm")`（`llm_factory.py:184-190`）。
- `IntentResponse`：`label / reason / confidence` + `init_values: InitValuesPayload`（具体对象，§5.11），承载 `target_position` 等入口字段；`extra='forbid'` 拒绝未知字段。
- 带上下文分类：`render_turn_input()` 用 `ROUTE_TURN_TEMPLATE` 拼入最近 2~3 轮、短期窗口 `short_term` 与长期记忆 `long_term` 的摘要（§5.8），解决「继续」「换成简历」「按我上次的偏好」等追问。
- 隐式通道异常 / 超时 / 未知 label → `default_agent`，`confidence=0`、`fallback_used=true`。
- 不使用 `LLMFactory.classify()`（QA 检索策略分类，非 Agent 路由）。
- 输入护栏：`check_input(message)`（`security/security.py:22-33`），命中发 `error(GUARDRAIL)` + `done`。
- `routing.source` 取 `card` / `template` / `rule` / `llm` / `fallback`，写入 turn 表，用于统计分类成本与卡片点击率。
- 显式通道命中「已注册但被停用（全局或租户维度）」的 Agent：直接返回 `error_code=FORBIDDEN`，**不静默兜底重路由**；完全未知的 `agent_type` 才走默认 Agent。运营在管理端关停卡片即生效（见 `api/v1/admin/agents.py` 的 `set_enabled`）。

### 4.4 四张卡片的入口逻辑

| 卡片 | 入口流程 | 执行链 | SSE 事件序列 |
| --- | --- | --- | --- |
| 智能问答 | 点卡片 → 进入输入态；直接提问 | QA 图同步流 | `routing_decision → progress → token → meta → done` |
| 模拟面试 | 点卡片 → 入口表单（`target_position` 必填、可选关联简历）→ 提交 | `InterviewAdapter.on_first_turn` 生成 `interview_id`、建业务行 + 注入 `initial_state` → 面试图生成开场白；追问按 `U:interview:<interview_id>` 复用同一状态机 | 同上，`done` 带 `current_stage/total_turns/is_finished/report_summary` |
| 考试批改 | 点卡片 → 表单（选 `exam_id`）+ 上传 `.docx` → 提交 | `attachment_service` 存 MinIO → 建 `agent_exam_submissions` 行 → `enqueue_task` → broker → exam 图 → HITL | `task_started → task_progress → task_result`；教师复核后追加 `task_result` |
| 简历分析 | 点卡片 → 上传 `.pdf` → 提交 | 同上，建 `agent_resume_reviews` 行 → `RESUME_REVIEW` → resume 图 | `task_started → task_progress → task_result` |
| 多 Agent 协同（内建 label） | 隐式通道分类为 `multi_agent`，或点「组合任务」模板问题 | `PipelineRunner` 生成 `PipelinePlan` → 逐步执行各 Agent（§4.9） | `pipeline_plan → pipeline_step_result* → pipeline_result` |

**入口字段校验**（编排层通用，不写 `if agent_type`）：`spec.entry_fields` 中 `required=true` 的字段缺失 → 发 `guidance` 事件（`code=INIT_REQUIRED`，文案取 `spec.init_prompt`）；`spec.accept_files` 声明的文件类型与 `attachments` 不匹配 → 发 `error(ATTACHMENT_INVALID)`。两种情况都不启动图。

**模板问题**：`spec.templates` 由 `GET /unified/agents` 下发；点击等价于「带 `agent_type` + 预填 `message` 自动发送」，走显式通道，零 Token、结果确定。

### 4.5 两阶段上传

SSE 是 POST JSON，不能承载 multipart，故文件走独立一步：

```
① POST /unified/attachments  (multipart, scope=unified:ask)
   ├─ 校验扩展名（spec.accept_files）、大小（config.qa.max_upload_mb）、非空
   ├─ 沿用 exam.py:76-93 / resume.py:90-102 的 MinIO 逻辑（抽成 attachment_service）
   ├─ 写 agent_file 或临时引用记录（tenant_id/user_id 隔离）
   └─ 返回 { file_ref, filename, size }       ← 不建业务行、不投 Outbox

② POST /unified/chat/stream { agent_type, entry_values, attachments:[file_ref], ... }
   ├─ adapter 校验 file_ref 归属与类型
   ├─ 建业务行（带 turn_id / U / trace_id）
   ├─ enqueue_task(TaskType.EXAM_REVIEW | RESUME_REVIEW, data={...})
   └─ SSE 推 task_started
```

`agent_file` 记录由 `attachment_service` 管理；孤立引用（上传后未发起任务）由现有清理策略处理，不进入会话历史。

### 4.6 任务事件回流与 HITL 闭环

| 环节 | 关联方式 |
| --- | --- |
| `enqueue_task` | `data` 带 `turn_id`、`thread_id=U`、`trace_id`、`agent_type`、`artifact_id`（`submission_id`/`review_id`） |
| broker handler | 入口 `trace_id_ctx.set(data["trace_id"])` 恢复链路；幂等检查仍按业务表 `biz_status`（`handlers/exam.py:21`、`handlers/resume.py:22`） |
| 回写业务表 | 图节点照旧回写 `status/weak_points/结果 JSON`；`task_progress` 事件由 `UnifiedConversationService.append_event()` 追加 turn 行 |
| 完成 | 追加 `event_type='task_result'` 的 turn 行，`payload` 存 `artifact_type` + `artifact_id` + 报告摘要 + `route_key`（跳结果页） |
| 用户回到会话 | 从 turn 表完整回放任务卡片；无需 SSE 在线 |
| exam 教师复核 | `POST /exam/submissions/{id}/confirm`（`exam.py:422-482`）保留独立端点；内部 `Command(resume=...)` 用 `orch.resume("exam", submission_id, ...)`（`exam.py:466`）→ 发布后追加 `task_result` turn |

> `review_required` 是 HITL 挂起时推给教师的**结果页跳转卡片**（`route_key` 指向保留的复核入口），复核动作本身不在统一入口内完成；见 §14 决策结论。

> exam 的 checkpoint 分区键保持 `submission_id`（HITL 挂起/恢复依赖），与统一会话的关联由业务表 `turn_id` 承担；因此 HITL 恢复链路零改动。

### 4.7 Dispatch 契约

```python
class AgentOutcome(BaseModel):            # 具体对象，见 §5.11
    content: str
    events: list[UnifiedEvent]
    state_patch: StatePatch
    persistence: PersistencePayload

async def dispatch(agent_type, unified_state, parent_cfg, entry: EntryPayload,
                   attachments: list[AttachmentRef]) -> AgentOutcome
```

**框架边界的 dict**：LangGraph 的 `ainvoke(inputs)` / `astream_events` 与 `tracing.with_callbacks(config)` 要求 dict-shaped 入参，这属于框架契约、不是业务属性。adapter 在边界处用 `model_dump(mode="json")` 转换，并在返回时用对应 `BaseModel.model_validate()` 复原；除 `unified_dispatch.py` 的转换函数外，业务代码不出现裸 `dict` 属性（D17）。

- `fork_config(cfg_U, thread_id=<分区键>)` 保留同一组 callbacks；**任何子图都不得使用裸 `U` 作 `thread_id`**，否则 QA / 面试图 State 会与薄图 `UnifiedState` 的同名 key（`messages` / `existing_summary`）写入同一 checkpoint 分区并互相覆盖。分区键规则：

  | 情形 | 分区键 | 说明 |
  | --- | --- | --- |
  | `spec.checkpoint_scope=True` | `U:<agent_type>:<artifact_id>` | `artifact_id` 为业务实例主键（面试 = `interview_id`），首次 `on_first_turn` 生成并写入 turn 行 `payload`，后续轮次从 `payload` 读取，**跨追问轮次恒定** |
  | `spec.checkpoint_scope=False` | `U:<agent_type>:<turn_id>` | 每轮唯一，checkpoint 无跨轮状态；本轮会话窗口由 `to_subgraph_input()` 从 `U` 注入 |
  | exam HITL | `submission_id` | 沿用现有挂起/恢复机制，`/confirm` 端点零改动 |
- `execution_mode` 决定分支：`stream` → `adapter.stream`；`task` → `adapter.on_first_turn` + 任务事件；`clarify` → 追问；`pipeline` → 计划卡片。编排层没有 `if agent_type == ...`。
- 子图 State 映射由 adapter 完成，**同名 key 不共享**；`to_subgraph_input()` 把 `UnifiedState.messages` 窗口与 `existing_summary` **单向注入**子图 state，子图不反向写回统一层（§5.8）。

### 4.8 checkpoint 分区总表

| 分区键 | 归属 | 内容 | 平台消费 |
| --- | --- | --- | --- |
| **`U`** = `agent_thread.id` | 统一编排层 | 会话级 `messages` 窗口、`existing_summary`（唯一记忆）、`routing`、`turn_index` | ✅ 唯一会话级 |
| `U:interview:<interview_id>` | 面试图执行态 | `current_stage` / `question_bank` / `total_turn_count` 状态机；`interview_id` 跨追问轮次不变 | ❌ |
| `U:qa:<turn_id>` | QA 图执行态 | 每轮独立、无跨轮状态；本轮消息窗口由 adapter 从 `U` 注入 | ❌ |
| `submission_id` | exam 独立异步 | HITL 挂起快照（沿用现有） | ❌ |
| `U:resume:<turn_id>` | resume 图 | 图现状不绑 checkpointer；该键仅用于 config 传递与 trace 关联 | ❌ |

**记忆唯一性**：4 张图的 `save_memory_node` 改为纯内存窗口裁剪、不再写任何独立摘要列；`existing_summary` 由统一层压缩写入 U checkpoint，adapter 每轮注入子图 state。业务表无 `summary` 列（§5.4）。

### 4.9 多 Agent 串联（Q14 已定，一期真跑）

`multi_agent` 不再只出计划卡片，一期即执行串联，复用 `Orchestrator.run_pipeline()` 的**分区键思路**（`orchestrator.py:38-46`：`f"{thread_id}:{agent_type}"`），但由统一编排层的 `PipelineRunner` 驱动，保证 State 隔离与观测闭环。

| 环节 | 实现 |
| --- | --- |
| 计划生成 | `PIPELINE_PLAN_PROMPT`（§3.11）+ `specs()` 生成 `PipelinePlan(steps: list[PipelineStep])`（§5.11）；先推 `pipeline_plan` 事件让用户可见 |
| 逐步鉴权 | 每步先 `scope_for_agent(step.agent_type)` + `has_scope()` + `is_enabled_for_tenant()`；任一步不合格 → 整体 `error(FORBIDDEN/AGENT_DISABLED)`，不启动任何图 |
| 逐步执行 | 每步 `fork_config(cfg_U, thread_id=f"{U}:{step.agent_type}:{turn_id}")` → `adapter.to_subgraph_input(...)` → `app_state.orchestrator.run_agent(step.agent_type, partition, inputs)` |
| 步骤间传递 | **不透传子图 state dict**：每步结果经 `adapter.from_subgraph_output()` 归一为 `PipelineCarry(content, artifacts)`（§5.11），下一步从 `PipelineCarry` 重建输入，避免 QA/面试/exam State 字段互相污染 |
| 事件与落库 | 每完成一步推 `pipeline_step_result` 并写一条 turn（`payload.artifact_*`）；全部完成推 `pipeline_result` 并写汇总 turn |
| 观测 | 整条 pipeline 一个 trace，每步一个 `agent.<agent_type>` span；`trace_id` 与 turn 行一致 |
| 失败 | 某步异常 → `error(PIPELINE_STEP_FAILED)` + `status='failed'` turn；已完成步骤结果保留可查，不回滚已落库数据 |
| 分区 | 每步独立分区键，与 §4.8 规则一致；不使用裸 `U` |

`PipelinePlan` / `PipelineStep` / `PipelineCarry` 均为 Pydantic 具体对象（§5.11）；`run_agent` 的 `inputs: dict` 只在转换边界出现（§4.7）。

## 5. 数据架构（单一归属键 B 方案）

### 5.1 唯一 id 体系

```
U           = agent_thread.id              唯一咨询会话
turn_id     = agent_unified_turn.id        唯一一轮（路由/进度/结果事件）
artifact_id = 各业务表主键 id              仅表示业务产物，不表示会话
```

**关联只有一条**：业务表 `turn_id` → `agent_unified_turn.id`；turn 行的 `thread_id = U`。反向：turn 行 `payload` 存 `artifact_type` / `artifact_id`。全库不再有 `S:qa` 派生键、`graph_name` 分区、`submission_id` 当会话键等第二套语义。

**三层 status 语义边界**（列名沿用现状，互不作为数据源、互不自动同步）：

| 层 | 列 | 取值 | 用途 |
| --- | --- | --- | --- |
| 会话 | `agent_thread.status` | `active` / `archived` | 会话列表与归档 |
| 轮次 | `agent_unified_turn.status` | `success` / `stopped` / `failed` | SSE 轮次结果、统计 |
| 业务 | 各业务表 `status` | `success/failed/partial`（QA）、`in_progress/finished/failed/deleted`（面试）、`ai_processing/pending_review/published`（exam）、`processing/done/failed`（resume） | 结果页筛选、broker 幂等、超时扫描、RAGAS |

### 5.2 会话 / 历史 / 记忆分工

| 数据 | 唯一落点 | 用途 |
| --- | --- | --- |
| 会话元信息 | `agent_thread` 一行（U） | 标题、状态、`updated_at`，租户+用户隔离 |
| **业务历史（source of truth）** | `agent_unified_turn`，一轮一行 | 全量正文 + 路由/进度/结果事件 + `trace_id`；分页、回放、审计、导出 |
| 运行时上下文 | `U` checkpoint 的 `messages` + `existing_summary` | 供 LLM 下轮输入；**不做历史查询源** |
| 业务明细 | 各业务表（QA 结果 / 面试报告 / 考试提交 / 简历评审） | 结果列表、报告、详情、RAGAS、HITL、超时扫描 |

**写入逻辑只有一处**：`UnifiedConversationService.append_turn()` 一次调用完成 turn 行、业务明细引用、`touch(U)`、checkpoint 写回。落库失败只记日志，不中断 SSE、不改成功语义。

### 5.3 新增表 `agent_unified_turn`

> DDL 生成遵循项目三条线（§11.1）：ORM 模型 → `python scripts/gen_schema.py` 生成 `schema.sql`（不手改）→ `scripts/migrations/` 增量脚本。


### 5.6 一次请求的写入时序

```
① 静态鉴权 + check_input                         失败 → 401/403 或 error 帧
② U = ThreadDao.get_or_create(session_key=S)     〔R1 必修〕
③ turn_id = 预分配 UUID
④ 双通道路由（显式跳过分类 / 隐式 LLM 分类）
⑤ 运行期动态鉴权（spec.scope + is_enabled_for_tenant）
      失败 → 写 status='failed' turn + SSE error+done，不调子图
⑥ 入口字段/附件校验（spec.entry_fields / accept_files）
      失败 → error(INIT_REQUIRED) 或 clarify
⑦ UnifiedGraph.ainvoke(cfg_U) → U checkpoint 持久化本轮 HumanMessage
⑧ dispatch：
      对话型 → adapter.stream → progress/token/meta
      任务型 → attachment_service 建业务行(turn_id) + enqueue_task → task_started
⑨ UnifiedConversationService.append_turn()
      一次写：turn 行 + payload.artifact_* + 业务明细 + touch(U) + checkpoint 写回
⑩ SSE done；ApiLogMiddleware 落 agent_api_call_log；Langfuse 异步导出
⑪ 异步补写：broker handler 完成 → 追加 task_result turn（同一 trace_id）
```

**失败边界**：⑤ 之外的落库失败只 `logger.exception` / `logger.warning`，不中断 SSE；被 stop / 流异常也写 `status=stopped/failed` 的 turn，补齐 `qa.py:213-214` 未实现的 failed 行。

### 5.7 多轮与路由一致性

- 同一 `session_id` 恒定解析到同一 `U`（R1 修复后），上下文、摘要、`last_agent_type` 连续。
- 每轮独立分类但带最近 2~3 轮；会话内切换 Agent 只换分支、不换 `U`。
- `turn_index` 单调递增，`UNIQUE(thread_id, turn_index)` 兜底并发；同一会话并发请求由 `U` 维度 Redis 短锁（`SET NX`，TTL 覆盖单次流最长时长）串行化。
- 入口字段由 `IntentResponse.init_values`（`InitValuesPayload`）或 `UnifiedChatRequest.entry`（`EntryPayload`）提供，两者均为 Pydantic 具体对象（§5.11）；缺失走 `clarify`，不使用硬编码默认值。首次成功后写入 `routing.init_values`，后续轮次复用。
- 会话摘要由统一层按 `spec.summary_policy` 压缩，写入 U checkpoint。

### 5.8 记忆分层（短期 + 长期一并接入，D20）

四层职责互不重叠，写入方唯一为 `UnifiedConversationService`：

| 层 | 存储 | 键 / 归属 | 生命周期 | 写入时机 | 读取时机 | 用途 |
| --- | --- | --- | --- | --- | --- | --- |
| **会话内滚动摘要** | `U` checkpoint `existing_summary` | `thread_id=U` | 会话存续 | 每轮 `append_turn()` 按 `spec.summary_policy` 压缩 | `load_context` 注入子图 state | LLM 上下文预算控制；唯一会话内摘要 |
| **短期窗口** | Redis `t:{tenant}:u:{user}:session:{U}` | 三段隔离（`memory.py:15-25`） | `SHORT_TTL_S=1天` | 每轮 `append_turn()` 成功/停止/失败后 `push_short(U, ShortTermTurn)` | `load_context` 取最近 `spec.short_term_limit` 条 | 跨请求原文回放、进程重启后快速续接 |
| **业务历史** | `agent_unified_turn` | `thread_id=U` | 永久（一期不自动清理） | 每轮 `append_turn()` | 会话详情、产物列表、审计 | 唯一 source of truth |
| **长期记忆** | `agent_long_term_memory`（PG） | `(tenant_id, user_id, agent_id, block)` | 永久 | 摘要压缩时由 `LongTermMemoryExtractor` 抽取 `summary/fact/preference` 块 | `load_context` 取最近 10 条注入 `long_term` | 跨会话的用户事实、偏好、历史摘要 |

实现要点：

- **短期**：改造 `MemoryStore.push_short(thread_id, message: ShortTermTurn)` / `get_short(...) -> list[ShortTermTurn]`，入参与返回值均为 Pydantic 具体对象（D17）；Redis 内仍以 JSON 字符串存储，序列化只在 `memory.py` 内部完成。`ShortTermTurn` 含 `turn_id/role/content/agent_type/event_type/create_at`，不含任意 `dict` 字段。
- **长期**：`LongTermMemoryDao.append(...)` 保持标量入参；`list_recent(...) -> list[LongTermMemoryBlock]` 改为返回具体对象（D17）。`agent_id` 取 `unified` 或 `spec.agent_type`（由 `spec.long_term_blocks` 声明），`block` 只允许 `summary/fact/preference`。
- **抽取**：`LongTermMemoryExtractor` 在 `append_turn()` 内按阈值触发（每 N 轮或摘要压缩时），用 `LONG_MEMORY_EXTRACT_PROMPT`（§3.11）产出结构化 `list[LongTermMemoryBlock]`，逐条 `append_long()`；抽取失败只 `logger.exception`，不中断 SSE、不改变轮次状态。
- **注入**：`load_context` 把 `existing_summary`、`short_term`、`long_term` 写入 `UnifiedState`（均为具体对象/列表），`render_turn_input()` 按 `ROUTE_TURN_TEMPLATE` 拼入分类上下文；`to_subgraph_input()` 把摘要与相关长期记忆注入子图 system prompt。
- **降级**：Redis 不可用 → `short_term=[]`（`memory.py` 既有降级）；PG 异常 → `long_term=[]` + `logger.exception`；两者都不影响主链路与成功语义。
- **隔离**：Redis key 已含租户+用户；PG 查询强制 `tenant_id + user_id`；身份上下文缺失时按 `memory.py:66-68` 跳过写入，绝不跨用户共享。
- **归档与清理**：会话归档时删除该 `U` 的 Redis key，checkpoint 与 turn 行、长期记忆保留可查；长期记忆按 `(tenant,user,agent_id,block)` 保留最近 50 条，超出由清理任务删除最旧行；D5 上线前运维清空 `agent_long_term_memory` 历史行与旧 `session:*` Redis key。
- **不遗留**：`agent_long_term_memory` 表与 `MemoryStore` 本期真正接入生产链路（现状全仓无 `append_long` 调用点）；`embedding_id` 列保留为空串（DAO 默认），语义检索由 Milvus 文档库承担，不作为本期遗留项。

2. **动态校验**：`_rebuild_derived()` 用 `pydantic.create_model()` 依 `spec.entry_fields` 生成 `EntryValues_<agent_type>`（字段类型由 `EntryField.type` 映射、`required` 决定默认值、`options` 生成 `Literal`），请求到达时以 `TypeAdapter` 对 `EntryPayload.fields` 做二次校验；新增 Agent 不改统一层。V13 在启动期验证每个动态模型可构造。
3. **校验边界**：所有 DTO 设 `model_config = ConfigDict(extra="forbid")`；FastAPI 请求体自动 422；`EntryPayload` 的业务级校验失败 → `error(INIT_REQUIRED)`（不抛 HTTP 异常，SSE 内返回）。
4. **数据库 JSON 列**：turn 表 `payload` / `routing` 仍为 `JSON` 列（DB 层），写入统一 `model_dump(mode="json")`，读取统一 `Model.model_validate(row[...])`，裸 dict 只在 DAO 的序列化函数中出现。
5. **框架边界**：LangGraph `ainvoke(inputs)` / `config` 与 `Orchestrator.run_pipeline()` 的 dict 入参，按 §4.7 在 `unified_dispatch.py` 的转换函数中进出；既有 4 张图的 State 定义不在本次改造范围（D1）。
6. **配置对象**：`tracing.with_callbacks()` 的 `config` 是 LangChain 框架要求的 dict-shaped 结构，不属于业务 State/请求属性，保持现状。

### 6.4 异步任务观测

- `enqueue_task` 的 `data` 带 `trace_id`；broker handler 入口 `trace_id_ctx.set(...)` 恢复上下文，使 handler 内日志、Langfuse span、业务行回写与发起请求的 trace 对齐。

### 6.5 指标与日志

| 指标 | 数据源 | 告警建议 |
| --- | --- | --- |
| 路由分布 / 卡片点击率 | turn 表 `agent_type` / `routing.source` | 某 Agent 突降 → 提示词或 spec 异常 |
| 分类降级率 / 低置信度率 | `fallback_used` / `confidence` | > 阈值告警 |
| 各 Agent 失败率 / P95 延迟 / 任务耗时 | turn 表 `status` / `latency_ms` / 任务事件 | 分 Agent 告警 |
| token / LLM 调用数 | Langfuse + turn `token_usage` | 成本看板 |
| 越权 / Agent 停用拒绝数 | 结构化日志 `error_code` | 安全审计 |
| 短期/长期记忆读写降级次数 | 结构化日志 `memory.*_degraded` | Redis/PG 健康度 |

日志级别沿用项目规则：`except` 块内 `logger.exception`；降级/未启用/无权限 `logger.warning`；成功 `info`。路由决策额外打一行结构化日志（`source / label / agent_type / confidence / latency / fallback_used / spec_version`）。

### 10.3 父子 scope 与 `build_tree` 升格问题

- `unified:menu` 与 `unified:ask` **必须同时授予** `teacher`/`student`，否则父节点被过滤后子项升格为顶级菜单；会话管理三个权限点按角色分配（学生可只给 `page`，教师额外给 `view`/`delete`，由超管在角色页配置）。
- 授权 SQL 按 `agent_role.name` 匹配（角色由超管创建，不写死 `role_id`）：

```sql
INSERT INTO agent_role_permission (role_id, scope)
SELECT r.role_id, s.scope FROM agent_role r
CROSS JOIN (VALUES ('unified:menu'), ('unified:ask'), ('unified_session:page'), ('unified_session:view'), ('unified_session:delete')) AS s(scope)
WHERE r.name IN ('student', 'teacher')
ON CONFLICT (role_id, scope) DO NOTHING;
```

- 菜单只控制入口显隐，不是安全边界（`menu_dao.py:1-3`）；接口仍须 `require_scope` + 运行期校验。
- 超管 `admin` 与 `tenant_admin` 不授予这两个 scope → 菜单不可见、接口 403（D3）。

### 10.4 spec → 菜单同步器

`AgentRegistry._rebuild_derived()`（每次 `load_from_db()` 末尾）执行幂等同步：

```python
async def sync_menus_from_specs(specs: list[AgentSpec]) -> None:
    """spec.menu 非空 → 按 path 幂等 upsert agent_menu；spec 下线 → visible=false。
    只处理 spec 声明的菜单；不触碰其它菜单行。"""
```

| 规则 | 说明 |
| --- | --- |
| 入参 | `specs()` 返回的 `list[AgentSpec]`（具体对象列表，D17）；菜单字段取自 `spec.menu: MenuSpec`（§5.11） |
| 幂等 | `INSERT ... ON CONFLICT (path) DO UPDATE SET name/icon/sort_order/scope/visible=EXCLUDED.*` |
| 父级 | `spec.menu.parent_path` 用子查询取 `parent_id`（种子已用此写法，`seed_data.sql:139`） |
| 下线 | `enabled=false` → `visible=false`（不物理删） |
| 冲突 | path 与非 spec 菜单冲突 → 启动期 V7 fail-fast |
| 种子关系 | 一次性初始菜单直接写进 `seed_data.sql` 最终形态；同步器只服务于运行时新增 Agent 的菜单 |
| 刷新 | 随 `publish_config_refresh("agent_registry")` 生效；前端 `GET /auth/menus` 或重新登录刷新 |

> 一期 4 个内置 spec 的菜单均在种子中，同步器为空跑，主要为后续扩展准备。
