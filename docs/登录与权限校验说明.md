# 登录与权限校验说明

> 说明多租户多智能体协作平台的「登录认证 → 请求身份校验 → 授权 → 菜单下发」四层如何判定。
> 相关代码：`backend/middleware/auth.py`、`backend/security/rbac.py`、`backend/security/security.py`、
> `backend/config/schemas.py`、`backend/data/postgres/auth/users.py`、`backend/data/postgres/auth/menu.py`、
> `dashboard/src/services/auth.ts`、`dashboard/src/services/http.ts`。
>
> 数据访问约定：`backend/data/postgres` 的模型类只用于生成 `schema.sql`，运行期不加载（按 `auth` / `agent` /
> `business` / `ops` 分域）；身份相关的读写应放在 `backend/data/dao/auth/` 里用 `text()` 写 SQL（见《数据库设计文档》§1.7）。
>
> **身份来源已定版为 token 单源（2026-10-24）**：请求只带 `Authorization: Bearer <JWT>`，
> `X-User-Id` / `X-Tenant-Id` 两个身份头已作废，`middleware/auth.py` 与本文件描述一致。

## 1. 判定层次

| 层 | 回答的问题 | 权威来源 | 失败码 |
|---|---|---|---|
| 登录认证 | 你是谁（凭证是否有效） | `user` 表（`username` + `password`） | 401 |
| 请求身份校验 | 本次请求是谁、在哪个租户 | JWT payload 的 `user_id` / `tenant_id` | 401 / 403 |
| 授权 | 你在该租户能做什么 | `agent_user_tenant` → `agent_role` → `agent_role_permission` | 403 |
| 菜单下发 | 你能看到哪些入口 | `menu` 表 + 当前 scopes | —（只隐藏，不拦截） |

三条贯穿全局的规则：

1. **登录只发生一次**，之后每个请求都重新查库授权，角色/权限变更即时生效，不依赖 token 内的快照。
2. **三级身份**：平台超管（唯一，由 `agent_user.is_super_admin` 标记，会话内无租户）→ 租户管理员（每租户 1 个，角色名 `tenant_admin`）→ 普通用户。超管判定只看 `is_super_admin` 布尔标记，不依赖租户或角色记录；租户管理员判定只看角色名；**租户写进 token，角色不写**，角色每次查库（见 §5.2）。
3. **agent 域只归超管**：Agent 定义、能力策略、插件、模型配置的读写，租户管理员和普通用户一律 403（见 §6.4）。
4. **超管不进业务**：超管 token 不带租户，`/api/v1/tenant/chat`、`/api/v1/tenant/orchestrator` 编排、会话、记忆、请求日志一律 403。超管只维护基建数据（租户、用户、角色、菜单、Agent 定义、配置中心）和跨租户查看这些基建数据（见 §6.8）。

## 2. 账号与密码

### 2.1 存储

| 字段 | 类型 | 说明 |
|---|---|---|
| `user.id` | BIGSERIAL | 用户 ID，全局唯一 |
| `user.username` | VARCHAR(64) UNIQUE | **登录名**，登录只查该列 |
| `user.name` | VARCHAR(64) | 显示名（前端展示、日志可读），不参与登录，不要求唯一 |
| `user.password` | VARCHAR(128) | **明文密码**，直接字符串比对 |
| `user.tenant_id` | BIGINT | 主租户（登录时优先选中；真实授权以 `agent_user_tenant` 为准） |

### 2.2 校验方式

- 密码**不哈希、不加密**，数据库存明文，登录时直接比对：`row.password == 明文密码`。
- 不引入 `passlib` / `bcrypt` / `argon2` 等哈希依赖，无加盐、无迭代。
- 不存在「明文与哈希混合」状态，因此也没有兼容升级逻辑。

实现注意：

- 请求体中的 `password` 字段**不得进入日志**：`api_log` 中间件默认不采集任何 body（`API_LOG_SAVE_BODY=false`），开启时也会脱敏。
- 任何响应模型都不含 `password`；列表/详情不 `SELECT *` 后直接抛出。
- 密码错误与用户不存在返回同一句 `用户名或密码错误`，不泄露账号是否存在。

### 2.3 不提供的能力

以下功能**不实现**，前端不放入口，后端不开放接口：

| 功能 | 状态 | 说明 |
|---|---|---|
| 自助注册 | ❌ | 账号由租户管理员创建；超管只建租户管理员账号（§6.2、§6.3） |
| 修改密码 | ❌ | 无用户自助改密 |
| 重置密码 | ❌ | 没有任何重置通道：无邮件/短信、无管理员重置接口、也不提供运维 SQL 方案 |
| 修改用户名 | ❌ | `username` 建号即定，接口层不开放 |
| 找回密码 | ❌ | 无 |
| 登录验证码 | ❌ | 登录仅校验用户名与密码两项 |
| 记住我 / 第三方登录 | ❌ | 仅账号密码 |

密码在**创建账号时一次性设定**，之后不再变更。账号密码遗失的，由创建者（超管或租户管理员）重新建号并在业务侧调整绑定，系统不提供原地恢复。

### 2.4 明文存储的边界

明文密码在以下位置可被读到，部署时需明确接受：

- 数据库直连查询、全量备份、慢查询日志里的参数。
- 运维排障的 `SELECT`、数据同步与导出脚本。
- 任何具备库读权限的账号。

适用前提是**内网、受控环境**：数据库不对公网暴露，账号权限收敛，备份加密存放。
若日后要改哈希，改动面很小：`password` 长度 128 足够放 bcrypt（60 字符），批量 `UPDATE` 后把比对改成 `verify` 即可，表结构不动。

## 3. 登录

### 3.1 接口

```
POST /api/v1/auth/login
Content-Type: application/json

{ "username": "admin", "password": "123456" }
```

`tenant_id` 可选：属于多个租户的用户（一个账号在不同租户各有一条分配）靠它在登录时选定租户，不带则走 `user.tenant_id`。会话内不提供切换，换租户就是带上新的 `tenant_id` 重新登录。

超管（`admin`，主租户）登录响应：

```json
{
  "code": 0,
  "msg": "",
  "data": {
    "token": "<JWT>",
    "expires_in": 86400,
    "user": { "user_id": 1001, "username": "admin", "name": "admin" },
    "is_super_admin": true,
    "is_tenant_admin": false,
    "current_tenant": null,
    "scopes": ["*"],
    "menus": [ { "id": 9, "name": "租户管理", "path": "/tenants", "icon": "ApartmentOutlined", "children": [] } ]
  }
}
```

响应里**没有 `tenants` 数组**，`current_tenant` 有两种形态：

| 身份 | `current_tenant` | 说明 |
|---|---|---|
| 普通用户 / 租户管理员 | 对象 | 就是本次会话的租户，与 `token.tenant_id` 一致 |
| 平台超管 | `null` | 超管没有会话租户，token 里也只有 `user_id` |

- 租户管理员和普通用户本来就只属于一个租户，数组没意义；要换租户靠登录时传 `tenant_id`。
- 超管不属于任何会话租户，需要看租户清单调 `GET /admin/tenants`，但那是管理数据，不是「切到该租户」。

三种身份的响应差异：

| 身份 | `current_tenant` | `is_super_admin` | `is_tenant_admin` | `scopes` | `menus` |
|---|---|---|---|---|---|
| 平台超管 | `null` | `true` | `false` | agent域+登录鉴权域+配置中心审核域（具体权限点，无 `*`） | 基建菜单全可见（§7.2） |
| 租户管理员 | 对象，`role=tenant_admin` | `false` | `true` | 角色权限点，无 `*` | 租户菜单 |
| 普通用户 | 对象，`role=student`/`teacher` | `false` | `false` | 角色权限点 | 按 scope 过滤 |

- `is_super_admin` / `is_tenant_admin` 放在顶层，所有身份都有，前端不再从 `current_tenant` 里读。
- 两个布尔值都由「角色名 + 租户 `is_primary`」推导，前端不要自己拼。
- 停用租户直接登录失败（403），不会出现在响应里。
- 不返回密码、不返回角色权限全表。

### 3.2 校验流程

```
POST /api/v1/auth/login
  ├─ 1. 按 username 查 user 表（唯一列）            → 查不到：401 用户名或密码错误
  ├─ 2. 明文比对 user.password                      → 不匹配：401 用户名或密码错误
  ├─ 3. 查 agent_user_tenant 取 (tenant_id, role_id)，join agent_role 取角色名、
  │     join tenant 取 is_primary / enabled
  ├─ 4. 判定身份（只看角色名与 is_primary，不看 role_id 数字）
  │      ├─ `agent_user.is_super_admin=true` → 平台超管；scopes=具体权限点（基建域 config/agent/model + 平台域 audit/message/auth/user/rbac/menu/tenant，无 *、无业务域）
  │      ├─ role='tenant_admin'             → 租户管理员
  │      └─ 其他                            → 普通用户
  ├─ 5. 租户停用或角色名不在内置目录 → 403 未分配租户或租户已停用
  ├─ 6. 超管（is_super_admin=true）到此结束：不选租户，current_tenant=null，token 只放 user_id
  ├─ 7. 其他身份选定当前租户：入参 tenant_id 有值 → 必须是该用户已分配且启用的租户（否则 403）；
  │     无值 → user.tenant_id 可用则用它，否则取第一个可用分配
  ├─ 8. 按 scopes 过滤 menu 表得到菜单树（超管 scope 覆盖全部菜单项，前端全量下发）
  └─ 9. 签发 JWT 并返回
```

要点：

- 超管判定只看 `agent_user.is_super_admin`（布尔标记），不依赖租户、角色名或 role_id。
- 租户管理员判定只认角色名 `tenant_admin`，不认 `role_id`。
- 停用租户的分配保留在库里，只在登录和请求期过滤，重新启用即恢复。
- 第 3 步的分配列表是后续所有判定的基础，一次查询取回，请求期不再重复查。
- 角色判定统一走 `backend/security/rbac.py` 的 `is_super_admin_role()` / `is_tenant_admin_role()`，接口层只读 `request.state` 上的布尔值。
- **token payload 分两种**：普通用户/租户管理员含 `user_id` + `tenant_id`；超管只含 `user_id`，**请求期不补租户**——超管的 `tenant_id` 恒为 `None`。角色与两个布尔量一律不进 token，否则「改角色即时生效」会失效。
- 多租户用户在登录时用 `tenant_id` 指定本次会话的租户，token 里就固定这个租户；要换只能重新登录，避免一个 token 里塞多租户状态。

### 3.3 鉴权例外

`/api/v1/auth/login`、`/api/v1/health` 不需要 `Authorization`；其余接口一律走 `get_current_user`。

## 4. 请求身份校验

### 4.1 必传凭证

| 凭证 | 必填 | 说明 |
|---|---|---|
| `Authorization: Bearer <JWT>` | ✅ | 登录签发的 token，唯一的身份来源 |

不读 `X-User-Id` / `X-Tenant-Id`，也不从 body / query / cookie 取身份。缺失 `Authorization` → **401**，不进入业务逻辑。

### 4.2 校验顺序（`get_current_user`）

| 步 | 校验 | 失败 |
|---|---|---|
| 1 | `Authorization` 存在且为 `Bearer` 形式 | 401 `缺少 Authorization` |
| 2 | JWT 验签、未过期 | 403 `凭证无效或过期` |
| 3 | `payload.user_id` 存在且为整数 | 401 `user_id 必须为整数` |
| 4 | `payload.tenant_id` 有值 → 走租户路径（第 5~7 步） | — |
| 4′ | `payload.tenant_id` 缺失 → 必须是平台超管：查 `agent_user_tenant` join `tenant`，要求存在 `is_primary` + `enabled` + 角色名 `admin` 的分配 | 403 `token 不含租户，且该用户不是平台超管` |
| 5 | 租户路径：查 `(user_id, tenant_id)` 的分配，join `agent_role` / `tenant` | 403 `用户 X 不属于租户 Y` |
| 6 | 租户 `enabled=true` | 403 `租户 X 已停用` |
| 7 | 判定 `is_tenant_admin`（角色名 `tenant_admin`）或普通用户 | — |
| 8 | 超管：`tenant_id=None`（无主租户时）或主租户 id、`is_super_admin=true`、`scopes=具体权限点（非 "*"）` | — |
| 9 | 解析角色与 scopes | 403 `角色解析失败` |

超管分支只看 `user_id`：不读 header、不读任何请求参数，也**不把主租户注入上下文**——`request.state.tenant_id` 与 `tenant_id_ctx` 都保持 `None`。

`tenant_of()` 遇到 `None` 直接 403 `平台超管无租户上下文`，这是所有按租户隔离业务的最后一道闸。

### 4.3 校验通过后写入

- `request.state`：`user_id`、`tenant_id`、`home_tenant_id`、`role_name`、`roles`、`scopes`、`is_super_admin`、`is_tenant_admin`
- contextvars：`app_state.user_id_ctx`、`app_state.tenant_id_ctx`（供审计、memory、限流、数据过滤全链路消费）。middleware 只写这一处，下游统一用 `app_state.get_user_id()` / `get_tenant_id()` 读。
- 所有按租户隔离的查询一律用 `tenant_id_ctx` 的值，**不接受请求体里的 tenant_id**；短期记忆 key 用 `t:{tenant}:u:{user}:session:{thread}`，用户身份缺失直接跳过读写。
- **超管的两个租户字段要分开**：`tenant_id` 恒为 `None`（没有会话租户，业务一律 403）；`home_tenant_id` 取 `user.tenant_id`（超管不挂租户时为 `NULL`，审计该列须可空），**只用于审计列的「操作者归属」**，不得参与任何数据过滤。

### 4.4 身份只来自 token

**所有接口的调用方身份只从 JWT payload 取**，不读 header、不读 body、不读 query、不读 cookie：

| 规则 | 说明 |
|---|---|
| body 禁止 `user_id` / `tenant_id` | 请求模型里不定义这两个字段；传了也不解析，Pydantic 默认忽略未知字段 |
| 不信任 body 身份 | 任何「body 里的 tenant_id 决定查哪个租户」的写法都算越权漏洞 |
| 超管接口例外 | `/api/v1/admin/*` 的 body 可以带 `tenant_id` / `user_id`，但那只是**操作对象**，绝不参与身份判定 |
| 审计与数据过滤 | `create_user_id` / `update_user_id` / `tenant_id` 一律取 contextvars，不取入参 |
| 超管无会话租户 | `tenant_of()` 对超管恒 403；不要写「超管自动看到全部租户数据」的分支，超管的数据范围是白名单制（§6.8） |

举例：`POST /api/v1/qa/ask` 的 body 只有 `{ "agent_type": "qa", "question": "..." }`，提交人与租户由 token 决定；如果前端想「替别人提问」，这条路在设计上不存在。

### 4.5 JWT 的作用

token 是唯一的身份来源，签名不可伪造也就意味着**拿到 token 等于拿到这个 user_id + tenant_id**：

- 不承载角色：角色每次查库，改角色即时生效。
- 承载租户：`tenant_id` 由签发端从该用户的真实分配里挑，客户端无法改。
- **超管 token 不带 `tenant_id`**：这不是「漏发」，而是能力上限——拿着它调业务接口一律 403，超管只能在基建域里活动。
- 没有刷新与吊销机制，有效期由 `JWT_EXPIRE_MINUTES` 控制；系统不提供改密（见 §2.3），所以也不存在「改密后旧 token 应失效」的问题。

## 5. 授权

### 5.1 数据模型

| 表 | 作用 | 关键结构 |
|---|---|---|
| `user` | 账号 | `id`、`username`（唯一）、`name`、`password`（明文）、`tenant_id` |
| `tenant` | 租户 | `id`、`name`、`enabled`、`is_primary`（主租户标记，不绑定具体 id） |
| `agent_user_tenant` | 用户-租户-角色分配 | 复合 PK `(user_id, tenant_id)` → 单租户内只任一角色 |
| `agent_role` | 角色目录（全局） | `role_id` 是入库用的业务键，`name` 才是判定依据；仅 `admin` 由种子预置，其余角色（含 `tenant_admin`）由超管在前端创建 |
| `agent_role_permission` | 角色→权限点 | 复合 PK `(role_id, scope)` |
| `menu` | 菜单目录 | `id`、`name`、`path`、`icon`、`parent_id`、`sort_order`、`visible`、`scope` |

角色与作用域：

| 角色名 | 允许出现的租户 | 能力 |
|---|---|---|
| `admin` | 由种子预置（全局唯一，以 `agent_user.is_super_admin` 为准） | 基建域 config/agent/model + 平台域 audit/message/auth/user/rbac/menu/tenant 全权限；不含任何业务域（qa/exam/interview/resume/knowledge） |
| `tenant_admin` | 任意租户（每租户恰好 1 个） | 本租户用户与角色配置，不可跨租户，不可碰 agent 域；**不预置，由超管在前端创建** |
| `student` / `teacher` 等 | 任意租户 | 业务使用；**不预置，由超管在前端创建**（scope 矩阵中的示例列） |

角色表里的 `role_id` 只是种子数据写库时用的编号（`1/2/3/5`，`4` 已随 `analyst` 角色删除而空缺、不复用），**代码里一律按 `name` 判定**：编号会随环境、迁移、重建而变，写死编号迟早出错。
超管唯一性由数据约束保证：全局只放 1 个 `admin` 角色分配，且它必须落在 `is_primary=true` 的租户里。

三张 RBAC 表之间无物理外键，为逻辑外键（引用完整性由代码控制）。

### 5.2 解析流程

```
token.tenant_id
  ├─ 有值 → 查 agent_user_tenant WHERE user_id=? AND tenant_id=?  join agent_role / tenant
  │          ├─ is_tenant_admin = role.name == "tenant_admin"
  │          └─ is_super_admin  = false
  └─ 无值 → 超管分支：查 agent_user_tenant JOIN tenant
            WHERE user_id=? AND tenant.is_primary AND tenant.enabled
            要求 role.name == "admin"，命中才放行
            → tenant_id = 主租户 id（无主租户为 None）, is_super_admin = true, scopes = 具体权限点（非 "*")
  → 写入 request.state / contextvars（tenant_id 可为 None）
```

- **判定只看 `agent_user.is_super_admin`（布尔标记）与角色名 `tenant_admin`**：接口层只读 `request.state` 上的布尔值，不重复比字符串。
- **不做硬编码常量兜底**：`DEFAULT_ROLES` 只作为种子写入数据库，请求期一律查表。
- 数据库不可用、分配不存在、租户已停用 → 403 `角色解析失败` / `无角色`（宁可不放行）。
- 超管的权限点由种子里 `admin` 角色的具体 scope 列表给出（基建域 + 平台域，不含业务域），不再用全局 `*`。
- 超管判定**只在 token 无 `tenant_id` 时进行**；带租户的 token 即使该用户在主租户也有分配，也按租户身份处理，不会升级成超管。

### 5.3 校验依赖

```python
# 角色校验（少数场景，如只允许教师以上）
@router.get("/xxx", dependencies=[Depends(require_role("admin", "teacher"))])

# 权限点校验：scopes 含全部指定 scope；"*" 通配
@router.post("/xxx", dependencies=[Depends(require_scope("exam:update"))])

# 仅超管
@router.get("/api/v1/admin/tenants", dependencies=[Depends(require_super_admin())])

# 仅当前租户管理员（超管不自动通过）
@router.get("/api/v1/tenant/users", dependencies=[Depends(require_tenant_admin())])

# 业务域：整个 router 挂在租户上下文上，超管一律 403
router = APIRouter(dependencies=[Depends(require_tenant())])
@router.post("/chat")
async def chat(...): ...
```

`require_scope` 在依赖注册期校验声明是否为合法 `Scope` 枚举成员，拼错直接抛 `ValueError`。
`require_super_admin` 读 `request.state.is_super_admin`，`require_tenant_admin` 只读 `is_tenant_admin`（不含超管），均不额外查库。

### 5.4 Agent 可用的三重判定

1. `agent.enabled = true`（全局开关）
2. `agent_capability_policy[tenant_id].enabled = true`（租户开通策略，未配置视为开通）
3. 调用方 scopes 覆盖该 Agent 所需权限点（如 `exam:ask`）

前两项由 `AgentRegistry` 在请求期判定，第三项由接口上的 `require_scope` 判定。
超管进不了这条链路：它没有会话租户，`require_tenant()` 在入口就 403，这三项对它不适用。超管的约束换成 §6.8 的白名单。

`POST /api/v1/chat` 是统一入口，路由到哪个 Agent 才知道需要哪个权限点，所以在 SSE 流内按路由结果校验一次（`qa:ask`/`resume:ask`/`exam:ask`/`interview:ask`），不满足就发 `error` 事件收尾。

以上是「这个 Agent 能不能被使用」。而「Agent 定义本身能不能改」属于 agent 域，只有超管可以，见 §6.4。

## 6. 租户管理与 agent 域边界

### 6.1 三级身份

| 身份 | 判定 | 数量 | 谁能维护 | 能力 |
|---|---|---|---|---|
| 平台超管 | 租户 `is_primary=true` 且角色名 `admin` | 全局唯一 | 种子固定，接口不提供增删，**不可删除** | 租户 CRUD、指定各租户管理员、角色权限点、agent 域、全量用户只读；**不能发起业务（§6.8）** |
| 租户管理员 | 角色名 `tenant_admin`（不预置，由超管创建） | 每租户**恰好 1 个**，**不可删除** | **只能由超管指定或更换** | 本租户普通用户的增删与角色配置 |
| 普通用户 | 角色名 `student` / `teacher` 等（不预置，由超管创建） | 不限 | **只能由本租户管理员维护** | 业务使用 |

维护边界是互斥的：

- 超管不直接管普通用户，只负责「谁当这个租户的管理员」。
- 租户管理员管不到别的租户，也不能自己任命管理员或转让管理员身份。
- 判定时机：每次请求查分配时顺带计算，不缓存、不写 token，权限变更即时生效。
- 超管没有「切到租户」这回事：它不持有会话租户，也读不到会话、记忆、请求日志；「能管这个租户」不等于「能看这个租户的业务数据」。

### 6.2 平台超管接口（`/api/v1/admin/*`，`require_super_admin`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/tenants` | 全部租户（含 `enabled`、管理员 `username`、用户数） |
| POST | `/admin/tenants` | 新建租户（`is_primary` 不可指定，恒 `false`） |
| PUT | `/admin/tenants/{id}` | 改名 / 启停（`enabled`）；主租户禁止停用 |
| PUT | `/admin/tenants/{id}/manager` | 指定或更换该租户管理员，body `{username, name?, password?}` |
| GET | `/admin/users` | 全量用户只读（含各自租户与角色），支持 `tenant_id` / `username` 过滤 |
| GET | `/admin/roles` | 角色目录与权限点 |
| PUT | `/admin/roles/{role_id}/permissions` | 覆盖角色权限点，保存即生效（超管「配所有权限」的入口） |
| PUT | `/admin/rbac/users/{user_id}/role` | 改任意租户用户的角色，body `{tenant_id, role}`，可授 `student` / `teacher` / `tenant_admin` |
| GET | `/admin/audit/logs` | 审计日志，可传 `tenant_id` 过滤，不传查全量 |
| GET | `/admin/config/**` | 配置中心读取（全局配置，无租户维度） |
| PUT | `/admin/config/**` | 配置变更 / 复核，仅超管 |

`PUT /admin/tenants/{id}/manager` 的语义：

- `username` 已存在 → 直接把该用户绑到该租户并设 `tenant_admin` 角色。
- `username` 不存在 → 用 `password` 建号，再绑为管理员（超管建号只走这一条路径）。
- 原管理员在同一事务内被移除（DELETE 其 `agent_user_tenant` 记录），不退租也不降级为其他角色（角色体系仅 `admin` 预置，`student` 已不存在）。
- 该接口不提供「把某人设为普通用户」「改普通用户角色」的能力，那些只有租户管理员能做。
- 管理员只能更换，不能删除：删掉之后该租户就没人能管了，接口一律 409 `租户管理员不可删除，请先更换`。

超管仍然没有 `POST /admin/users`：新建普通账号只在租户管理员那边发生，便于追责。
超管在权限中心能做的是「改已有用户的角色」（`PUT /admin/rbac/users/{user_id}/role`）和「改角色权限点」。
`admin` 自身不通过该接口变更，仍只有种子写入 + 更换机制。

### 6.3 租户管理员接口（`/api/v1/tenant/*`，`require_tenant_admin`）

租户一律取自 token 的 `tenant_id`，body 不接受 `tenant_id`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/tenant/users` | 本租户用户列表（含角色名，管理员本人标记出来） |
| POST | `/tenant/users` | 在本租户建普通用户，角色只能是 `student` / `teacher` |
| PUT | `/tenant/users/{user_id}/role` | 改本租户内角色，只能在上述两者间改 |
| DELETE | `/tenant/users/{user_id}` | 从本租户解绑普通用户（不删 `user` 记录） |
| GET | `/tenant/roles` | 本租户可分配的角色（上述三者） |
| GET | `/tenant/audit/logs` | 本租户审计日志，`tenant_id` 强制取 token，忽略入参 |

权限中心页面在租户管理员这边就是上表的 `/tenant/users` + `/tenant/roles`，不另设一套接口：
用户列表即权限列表，改角色即改权限。角色权限点（`agent_role_permission`）不在其能力范围内。

- `require_tenant_admin` 只认 `is_tenant_admin`，**超管不自动通过**：普通用户的维护入口只有租户管理员。
- 租户管理员不能看别的租户、不能建租户、不能改角色权限点、不能把任何人设成 `admin` 或 `tenant_admin`。
- 对管理员自己的记录不可改角色、不可解绑（要换人只能找超管）。

### 6.4 agent 域边界

agent 域指以下资源与接口，**仅超管**可读写。这些接口都在 `backend/api/v1/admin/` 包里，路径前缀 `/api/v1/admin`，装配处统一挂 `require_super_admin()`：

| 范围 | 资源 |
|---|---|
| Agent 定义 | `agent` 表、`/api/v1/admin/agents/*` |
| 能力策略 | `agent_capability_policy`（含租户开通开关） |
| 插件 | `agent_plugin`、`/api/v1/admin/plugins` |
| 模型配置 | `agent_model_config`、`/api/v1/admin/models/*` |

- 对应菜单 `/agents`、`/tools`、`/models` 的 scope 为 `agent:read` / `agent:write` / `model:read`，只授予超管角色。
- 会话使用（`/sessions`、`qa:ask`）不属于 agent 域，按租户正常开放。
- 租户管理员调用上述接口 → 403 `仅平台管理员可操作`。
- 这些表属于基建：超管可读写，但读写它们不产生会话，也不需要租户上下文。

### 6.5 写入约束

1. **超管唯一**：由 `agent_user.is_super_admin` 标记，全局仅 `admin` 一个用户拥有；身份解析以此为准，不依赖 `agent_user_tenant` 记录。
2. **租户管理员恰好 1 个**：每租户 `tenant_admin` 必须有且仅有 1 条，只能经 `PUT /admin/tenants/{id}/manager` 产生。新建租户时该值为空，需超管先指定管理员才能使用。
3. **唯一性由库层唯一索引兜底**：`uk_tenant_primary`（主租户至多一个）、`uk_aut_tenant_admin`（每租户一个租管）两条部分唯一索引保证入库数据正确，应用层再包一层友好报错；超管不写 `agent_user_tenant`，无对应索引。
4. **超管与租户管理员不可删除**：只允许「更换」不允许「删除」。删超管 = 平台失去管理入口，删管理员 = 该租户无人可管，接口一律 409。
5. **更换是原子的**：指定新管理员时，同一事务内移除原管理员记录再写入新的 `tenant_admin`，不允许出现 0 个或 2 个管理员的中间态。
6. **维护入口互斥**：租户管理员只能操作本租户的 `student` / `teacher`；超管没有改普通用户角色的接口，也没有 `POST /admin/users`。
7. **管理员自身不可改**：租户管理员不能改自己的角色、不能解绑自己，换人只能找超管。
8. **防自锁**：不能降级最后一个 `admin`（409 `不能移除最后一个超管`）；主租户不能停用（400 `主租户不允许停用`）。
9. **内置角色不可删**：`agent_role` 中的内置角色只允许改权限点，不允许删除，`name` 不可改。
10. **引用合法**：`role_id` 必须存在于 `agent_role`，`tenant_id` 必须存在于 `tenant`。
11. **幂等**：重复指定同一管理员不报错，视为无变更并记一条空操作审计。
12. **改权限即时生效**：`PUT /admin/roles/{role_id}/permissions` 保存后下一次请求即按新权限校验，**无二次审批**，仅记审计。
13. **审计留痕**：写操作落 `agent_audit_log`，`operator_user_id` 取 token 身份，`detail` 记录目标与变更前后角色。
14. **审计只读**：`agent_audit_log` 不提供任何增删改接口，写入只由业务操作在事务内完成；查询时 tenant_admin 强制按本租户过滤，忽略请求里的 `tenant_id`。

| action | 场景 |
|---|---|
| `rbac.grant` | 新增绑定 / 改角色 |
| `rbac.revoke` | 解绑 |
| `rbac.role_permissions` | 改角色权限点（记录改前/改后集合） |
| `tenant.create` / `tenant.update` | 租户维护 |

审计记录含 `operator_user_id`、目标 `user_id`/`tenant_id`、`detail`（JSON），供「审计日志」页查询。

### 6.6 权限点

| scope | 含义 | student | teacher | tenant_admin | admin |
|---|---|---|---|---|---|
| `tenant:read` | 查看租户列表 | ❌ | ❌ | ❌ | ✅ |
| `tenant:write` | 新建/修改租户 | ❌ | ❌ | ❌ | ✅ |
| `rbac:read` | 查看角色与用户 | ❌ | ❌ | ✅ | ✅ |
| `rbac:write` | 配本租户用户角色 | ❌ | ❌ | ✅ | ✅ |
| `agent:read` | 查看 Agent 定义 | ❌ | ❌ | ❌ | ✅ |
| `agent:write` | 维护 Agent / 策略 / 插件 | ❌ | ❌ | ❌ | ✅ |
| `model:read` | 查看模型配置 | ❌ | ❌ | ❌ | ✅ |
| `model:create` | 新增模型配置 | ❌ | ❌ | ❌ | ✅ |
| `model:update` | 修改配置 / 设默认 / 探测连通性 | ❌ | ❌ | ❌ | ✅ |
| `model:delete` | 删除模型配置 | ❌ | ❌ | ❌ | ✅ |
| `config:read` | 进入配置中心 | ❌ | ❌ | ❌ | ✅ |
| `config:update` | 配置变更 / 复核 | ❌ | ❌ | ❌ | ✅ |
| `audit:read` | 查看审计日志 | ❌ | ❌ | ✅ | ✅ |

- `admin` 角色在种子里是 `*`，上表仅表示语义，不需要逐条写入 `agent_role_permission`。
- `model:*` 四个权限点（read / create / update / delete）都在 `backend/security/rbac.py` 的 `Scope` 枚举里，只有 `admin` 的 `*` 覆盖，其他角色一律没有。
- `config:*` 只授予超管：配置中心是全局配置（`agent_config_approval` 无 `tenant_id`），没有租户维度可分。
- `audit:read` 只授予超管与租户管理员；审计域**没有 `audit:update`**，日志只读，无可写的接口。
- `tenant_admin` 角色没有 `agent:*`、`model:*`、`config:*`、`tenant:*`，因此看不到也调不通这些页面。
- 租户管理员即便有 `rbac:write`，接口层也强制 tenant 取 token 里的租户，改不到别的租户。

### 6.7 配置中心 / 审计日志 / 权限中心的数据范围

| 页面 | 可见角色 | 菜单 scope | 超管数据范围 | tenant_admin 数据范围 |
|---|---|---|---|---|
| 配置中心 `/config` | 仅超管 | `config:read` | 全部全局配置 | 不可见（角色无 `config:read`） |
| 审计日志 `/audit` | 超管、tenant_admin | `audit:read` | 全租户，可按 `tenant_id` 筛 | 强制 `tenant_id = token 租户` |
| 权限中心 `/rbac` | 超管、tenant_admin | `rbac:read` | 全部租户用户角色 + 角色权限点 | 本租户用户角色，限 `student` / `teacher` |

三条共同的实现要求：

1. **过滤在服务端做**：tenant_admin 的 `tenant_id` 一律取 `request.state.tenant_id`，请求里的 `tenant_id` 参数直接忽略，不能靠前端自觉。
2. **可见靠菜单 scope，可调靠接口校验**：菜单不下发只是不显示入口，接口仍要挂 `require_scope` / `require_super_admin` / `require_tenant_admin`。
3. **三个页面都没有写审计的接口**：审计日志只读；配置中心的写操作和权限变更由业务逻辑落审计，不走审计页面。

超管查全量审计时，页面顶部给租户筛选下拉，选项取自 `GET /admin/tenants`；tenant_admin 页面不显示该下拉。

### 6.8 超管的能力边界（基建 vs 业务）

超管 token 不含租户，所以它**进不了任何按租户 / 用户隔离的业务链路**。这条边界不靠 `scope` 表达，靠 `tenant_id is None` 自然成立。

**可以操作（基建数据）**

| 域 | 数据 | 接口 |
|---|---|---|
| 租户 | `tenant` | `/admin/tenants/**` |
| 账号 | `user`（只读，密码列不返回） | `/admin/users` |
| 授权 | `agent_user_tenant`、`agent_role`、`agent_role_permission` | `/admin/roles/**`、`/admin/rbac/**` |
| 菜单 | `menu` | 随 `/auth/menus` 下发 |
| Agent 定义 | `agent`、`agent_capability_policy`、插件清单 | `/agents/**` |
| 配置中心 | `agent_config_approval`、`agent_config_review`、Nacos | `/admin/config/**` |
| 审计 | `agent_audit_log`（权限 / 配置变更） | `/admin/audit/logs` |

**不能访问（业务数据）**

| 数据 | 原因 | 表现 |
|---|---|---|
| `agent_thread`（会话与消息） | 按 `(user_id, tenant_id)` 隔离 | 403 `平台超管无租户上下文` |
| 记忆（Milvus 分区） | key 含 `t:{tenant}:u:{user}` | 不进入检索链路 |
| `agent_api_call_log` | 含提问原文，属于用户请求数据 | 不提供超管查询接口 |
| 人工升级工单（`chat/escalations`） | 业务工单 | 403 |
| `/chat`、`/agent/orchestrator` | 发起对话 / 编排 | 403 `平台超管不可发起业务请求` |

三条实现要求：

1. **白名单制**：admin 域接口只挂 `require_super_admin()`，不挂 `require_tenant()`、不调 `tenant_of()`；业务域 router 反过来，一律挂 `require_tenant()`。
2. **不做「以租户视角查看」**：`/admin/tenants/{id}/overview` 这类跨域只读接口不提供。要看某租户的业务数据，就用该租户的账号登录。
3. **审计的租户列**：超管写操作的 `create_tenant_id` 取 `home_tenant_id`（主租户），那是「操作者归属」，不代表它能读写该租户的业务数据。

## 7. 菜单下发

### 7.1 `menu.scope` 语义

| 值 | 含义 |
|---|---|
| `NULL` | 登录即可见 |
| 具体 scope（如 `qa:read`） | 用户 scopes 含该值 |
| 用户 scopes 含 `*` | 基建菜单全可见（超管，仍受 §7.2 第 4 条白名单约束） |

### 7.2 过滤规则

```
可见菜单 = menu 中满足以下全部条件的项
  1. visible = true
  2. scope IS NULL OR scope ∈ 用户 scopes OR 用户 scopes 含 "*"
  3. 父菜单可见（parent_id = 0 视为可见）
  4. 超管：path ∈ SUPER_ADMIN_MENU_PATHS
按 sort_order 升序组装为树
```

菜单只控制入口显隐，**不是安全边界**。接口侧仍必须挂 `require_scope`，否则直接 curl 照样能调。

- **超管菜单是白名单**：`SUPER_ADMIN_MENU_PATHS = {"/tenants", "/rbac", "/audit", "/agents", "/tools", "/models", "/config"}`。`/dashboard`、`/sessions`、`/qa` 虽然对超管的 `*` 可见，但被白名单挡掉——超管不看业务数据。白名单按**根路径匹配且自动包含其所有子菜单**（如 `/audit` 含 `/audit/operation` 等三个子项、`/config` 含申请/审核、`/rbac` 含租户管理/用户管理），实现见 `menu_dao.build`。
- `/agents`、`/tools`、`/models`、`/config` 都只有超管有对应 scope，其他角色菜单直接不出现。
- `/audit` 只对超管与租户管理员下发，展开为三个子菜单（业务审计 / 登录日志 / 调用日志）；tenant_admin 进页面后只能看到本租户日志。
- `/rbac` 菜单用 `rbac:read` 判断可见性：能进页面就可能只有读权限，写操作由接口单独校验 `rbac:write`；其下挂「租户管理」（scope `tenant:read`，仅超管）与「用户管理」（scope `rbac:read`，超管与 tenant_admin）。
- `/tenants` 已作为「权限中心」子项存在（不再独立顶级）；`tenant:read` 仅授予 admin，租户管理员管本租户用户走 `/rbac` 页，接口是 `/tenant/*`。

### 7.4 菜单接口

| 场景 | 接口 |
|---|---|
| 登录 | 响应体直接带 `menus`（省一次往返） |
| 登录后重取 | `GET /api/v1/auth/menus`（租户取自 token） |

不支持会话内切换租户：超管没有会话租户，其余角色只有一条分配。换租户只能重新登录。

## 12. 前端要点

- `login()` 调 `POST /api/v1/auth/login`，删除 `admin/admin` 硬编码与 `DEFAULT_ACCOUNT`；多租户用户由调用方决定是否传 `tenant_id`。
- 成功后 `localStorage` 存 `ap_token`、`ap_user`、`ap_menus`；`ap_tenant_id` 只在 `current_tenant` 非 `null` 时写（超管不写）；`is_super_admin` / `is_tenant_admin` 从响应顶层读，不自己推断。
- `http.ts` 统一注入凭证，业务代码不手动传：

```ts
headers: {
  'Content-Type': 'application/json',
  ...(token ? { Authorization: `Bearer ${token}` } : {}),
}
```

- 401 → 清 localStorage 跳 `/login`；403 → 提示「无权限」并留在当前页。
- 侧边栏由 `ap_menus` 渲染；`path → 组件` 映射仍由前端维护（白名单），未在菜单中的 path 显示 404 提示。
- 不提供租户切换器：租户随 token 固定。超管要看其他租户的清单，去「租户管理」页（`GET /admin/tenants`）。
- 登录页无「注册」「忘记密码」入口，也无验证码控件；账号密码错误只提示同一句文案。

## 13. 错误码与排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `401 缺少 Authorization` | 未登录或 token 未注入 | 检查 localStorage 的 `ap_token` 与 `http.ts` 拦截器 |
| `401 用户名或密码错误` | 账号不存在或密码不匹配 | 核对 `user.username`、`user.password`（明文） |
| `403 该用户未分配任何租户` | `agent_user_tenant` 无记录或租户全停用 | 补分配（§9.3）或启用租户 |
| `403 token 不含租户，且该用户不是平台超管` | 用一个没有租户的 token 调接口，但该用户不是超管 | 重新登录；核对 `agent_user_tenant` 里「主租户 + admin」的分配 |
| `403 平台超管无租户上下文` | 超管调了业务接口（chat / 会话 / 记忆） | 超管只走 `/admin/**`、`/agents/**`、`/config/**`；业务操作换租户账号 |
| `403 用户 X 不属于租户 Y` | token 的 tenant 不在该用户的分配里 | 正常不该出现：要么分配被删，要么 token 被伪造。重新登录并核对 `agent_user_tenant` |
| `403 租户 Y 不存在` | 切到了库里没有的租户 | 核对 `tenant` 表 |
| `403 租户 Y 已停用` | `tenant.enabled=false` | 超管在租户管理里启用 |
| `403 仅平台管理员可操作` | 租户管理员调了 agent 域接口 | 换超管账号，或不该开放该入口 |
| `403 凭证无效或过期` | 签名不匹配或已过期 | 重新登录换 token；核对 `JWT_SECRET` 是否被改 |
| `403 缺少 scope [...]` | 接口挂了 `require_scope`，角色无该权限 | 调角色权限或换账号 |
| `403 角色解析失败` | 数据库不可用 | 查连接与 `agent_role_permission` |
| `400 admin 角色只允许存在于主租户` | 非主租户出现 `admin` 角色分配 | 清理脏数据，超管角色只允许落在 `is_primary=true` 的租户 |
| `400 主租户不允许停用` | 对 `is_primary` 租户置 `enabled=false` | 保持主租户启用 |
| `403 仅本租户管理员可操作` | 超管调了 `/tenant/*` | 普通用户由该租户管理员维护 |
| `409 该租户暂无管理员` | 新租户还没指定管理员就拿去登录 | 超管先调 `PUT /admin/tenants/{id}/manager` |
| `409 不能移除最后一个超管` | 会把 `admin` 分配清空 | 超管只能更换不能删除 |
| `409 租户管理员不可删除，请先更换` | 试图解绑唯一管理员 | 先 `PUT /admin/tenants/{id}/manager` 换人 |
| 菜单少了某项 | 该菜单 `scope` 不在当前权限内 | 查 `menu.scope` 与角色权限点 |
| 启动报 `JWT_SECRET 未配置` | 未设密钥 | 在 `.env` 配 `JWT_SECRET` |
