# 一、2 分钟项目介绍（可直接背）

> 连续朗读即可，段间只做自然停顿。按「为什么做 → 做了什么 → 怎么做 → 结果」推进，重点在怎么做（三个智能体、路由、图执行、审批恢复）。

「上线前的 SQL 变更评审全靠 DBA 人工看锁风险、影响行数、慢 SQL 和规范符合度，一条 DDL 要翻好几处，标准不一、结论留不下来，也没有统一的沙箱验证，风险全压在上线那一刻。

我做的是数据库变更治理中台：一条对话入口，把问规范、评审风险、人工审批、沙箱验证、放行输出 SQL 串成闭环。边界清楚——平台不执行生产，生产仍由 DBA 人工完成。

核心是三个智能体。知识问答答规范、流程、原理问题：文档父子片切分、扫描件 OCR，检索用 Milvus 的 dense 加 sparse 混合检索做 RRF 融合，再经 bge-reranker 精排，取首条分数当置信度，超过 0.45 走 RAG 并附来源，否则直接回答。变更评审针对待执行 SQL：四路并行拉锁信息、影响行数、慢 SQL 和元数据，汇总后做风险分级与优化建议，再交人工审批。变更发布针对已审批变更：影子库沙箱执行校验，人工放行后输出最终 SQL。

路由上，统一咨询是一张薄图：点卡片、模板或请求带 agent 类型直接分派；自由输入先按关键词规则分类，没命中交大模型分类，再失败兜底知识问答；路由结果用第一个 SSE 帧返回。

执行上，三个智能体各自独立编译图，编排层不写按类型分支；薄图只做路由、鉴权、入口校验和事件映射，通过适配器在「会话、智能体、轮次」三级分区的 checkpoint 上调用对应图，各图事件统一映射成一套 SSE 协议。卡片、模板、入口字段由后端下发，前端不写死，新增智能体零改动。

审批这块，评审和发布在关键节点用 interrupt 挂起，前端弹框；通过后走 resume，在同一条消息里继续流式输出。审批前的耗时和 token 先写进图状态，恢复后合并展示，等待时间不计入。

结果是一条对话走完提问、评审、审批、沙箱验证到放行的闭环，评审标准统一、过程可追溯；三个智能体共用一套事件协议和权限体系。」

# 二、题库（易 → 难）

> 每题给「要点」，面试时按要点展开即可，不必逐字背。

## A. 入门（项目与基础）

**A1. 一句话介绍你的项目。**
- 数据库变更治理中台：统一入口 + 知识问答/变更评审/变更发布三个智能体；
- 平台只做「评审 + 沙箱验证 + 输出 SQL」，不执行生产；
- 技术栈：FastAPI + LangGraph + PostgreSQL + Redis + Milvus + MinIO + RabbitMQ + React。

**A2. 为什么要做「统一咨询入口」？**
- 用户不用记多个入口/多个页面；
- 能力由后端 `AgentSpec` 下发（卡片、模板、入口字段），前端不写死 Agent；
- 新增 Agent 只加后端图 + spec，前端零改动。

**A3. 三个 Agent 分别做什么？**
- `qa`：知识库 RAG 问答（规范/流程/原理）；
- `db_review`：待执行 SQL 的静态风险评审 + 人工审批；
- `db_release`：已审批变更的沙箱验证 + 人工放行 + 输出 SQL。

**A4. 什么是 RAG？为什么需要它？**
- 检索增强生成：先检索知识库片段，再让 LLM 基于片段回答；
- 解决「模型不知道企业内部规范」和「幻觉」问题，答案可给出来源。

**A5. LangGraph 是什么？你用它解决了什么？**
- 基于状态图的 Agent 编排框架：节点 = 处理步骤，边 = 流转，State 跨节点共享；
- 我用它做：多节点流水线（检索→分级→建议）、条件分支、`interrupt` 人工挂起、checkpoint 多轮恢复。

**A6. SSE 和 WebSocket 的区别？你为什么用 SSE？**
- SSE：单向（服务端→客户端）、基于 HTTP、自动重连、实现简单；
- WebSocket：双向、需协议升级；
- 我只需要「流式输出答案」，不需要客户端持续上行，所以 SSE 更轻；且已有 HTTP 鉴权体系可复用。

**A7. JWT 认证流程说一下。**
- 登录校验账号密码 → 签发 JWT（user_id/tenant_id/jti）；
- 请求带 `Authorization: Bearer`，中间件验签 + 查 Redis 会话有效性；
- 权限从角色权限点集合判断；登出删 Redis `jti` 使 token 立即失效。

**A8. 为什么运行时不用 ORM？**
- DAO 全部 `text()` 手写 SQL，性能与 SQL 可控（复杂聚合、JSONB、`ON CONFLICT`）；
- ORM 模型只用于 `gen_schema.py` 生成 DDL；
- 代价是开发成本高，用统一 `fetch_all/fetch_one/execute_write` 封装降低重复。

**A9. Redis 在你项目里承担什么？**
- 登录会话（jti + 滑动续期）；
- 短期对话记忆（`t:{tenant}:u:{user}:session:{thread}`，TTL 1 天，`ltrim` 限长）；
- 停止流式标记、配置刷新版本号、看板缓存。

**A10. 为什么用 MinIO？**
- 存知识库文档原件与附件；
- S3 兼容，本地可跑，和对象存储解耦，便于换云。

## B. 中级（核心链路）

**B1. 讲一下 RAG 的完整链路。**
- 解析（PDF/Word/文本，扫描件 OCR）→ 父子片切分 → 子片向量化写 Milvus；
- 查询：查询分类（精确/宽泛/精准）→ 必要时多查询改写或 HyDE；
- 混合检索（dense + sparse，RRF 融合，取 topK 候选）→ bge-reranker 精排 → 取 final_k；
- 置信度 = 首条精排分数，`>= 0.45` 走 RAG 生成，否则直答/联网兜底。

**B2. 为什么要混合检索？RRF 是什么？**
- dense（语义）召回同义改写，sparse（BM25/稀疏）召回专有名词、编号、SQL 关键字；
- 两路互补，单路都容易漏；
- RRF（Reciprocal Rank Fusion）：按排名融合 `Σ 1/(k+rank)`，不需要分数可比、鲁棒；
- 注意：RRF 分数只有 0.0x 量级，**只能排序不能当相似度**（这是我踩过的坑）。

**B3. 精排为什么必要？为什么不能直接用向量分数？**
- 向量相似度是「泛化语义」，对「命中但答非所问」区分度低；
- cross-encoder（bge-reranker）把 query 和 chunk 拼一起打分，精度高很多；
- 注意 cross-encoder 慢，所以先粗排 topK 再精排。

**B4. 父子片（small-to-big）解决什么问题？**
- 子片小（300 字）→ 向量更聚焦、召回准；
- 命中后回填父片（1200 字）→ 给 LLM 的上下文更完整；
- 只用子片会丢上下文，只用大块会稀释语义。

**B5. 置信度阈值怎么定？太低/太高有什么问题？**
- 太低：不相关内容也走 RAG → 幻觉/答非所问；
- 太高：总是走直答 → 知识库白建；
- 我用「首条精排分数」，初始 0.75 发现几乎达不到（reranker 分数分布 0.2~0.6），调到 0.45，并结合日志观察分布再微调。

**B6. 多轮对话的记忆你怎么分层的？**
- `agent_unified_turn`：每轮问答持久化（唯一真相源，用于回放/评测）；
- Redis 短期记忆：最近 N 条，TTL 1 天，供图内上下文；
- 摘要压缩：达到阈值（6 轮）把历史压成 summary，写回图状态；
- 长期记忆：从摘要里抽 `summary/fact/preference` 写 PG，跨会话复用。

**B7. 长期记忆什么时候写？为什么不是每轮都写？**
- 每轮写成本高（一次 LLM 抽取）且会重复污染；
- qa 在摘要触发时写；评审/发布在「审批通过/放行」这种关键结论点写；
- 用 `agent_id` 区分，读取时按 `AgentSpec.long_term_blocks` 各自加载。

**B8. HITL 你是怎么实现的？**
- 节点内 `interrupt(payload)` 让图挂起，checkpoint 保存现场；
- 前端收到 `interrupt` 事件弹审批框；
- 通过 `POST /resume` 用 `Command(resume=...)` 从断点继续，**同一个 SSE 连接继续推 token**；
- 审批前段统计写进 state，最终结果合并展示。

**B9. interrupt 挂起期间，服务重启会怎样？**
- 状态在 checkpoints（PostgreSQL）里，不依赖内存；
- 重启后 resume 仍能恢复（checkpoint 有 thread_id + ns）；
- 所以 checkpoint 不能随便清（这也是我"删会话只删 thread"的原因之一）。

**B10. 子图的 checkpoint 是怎么隔离的？**
- 父图 `thread_id = 会话`；
- 子图 `thread_id = {会话}:{agent}:{轮次}`，每轮独立；
- 好处：子图状态互不干扰，HITL resume 直达；代价：不是原生命名空间嵌套。

**B11. 为什么不用 LangGraph 原生 subgraph？**
- 原生 subgraph 编译期就要把节点接好，而我的 Agent 是**租户级动态注册**（DB 决定谁可用）；
- 原生嵌套 + HITL 恢复要走 `checkpoint_ns` 传播，复杂；
- 用 adapter 调用换来：动态路由、事件集中映射、HITL 简单；
- 我知道代价（状态要显式映射、checkpoint 不嵌套展示），所以做了 `to_subgraph_input/from_subgraph_output` 与分区约定。

**B12. 多租户隔离你在哪几层做了？**
- PG：所有业务表带 `tenant_id`，DAO 强制过滤；
- Milvus：`tenant_id` 作为分区键，检索带 `expr`；
- Redis：key 前缀 `t:{tenant}:u:{user}:`；
- MinIO：按租户前缀组织对象键；
- 网关/接口：`CurrentUser.tenant_id` 来自 JWT，不信任请求头。

**B13. RBAC 怎么设计的？**
- 用户 → 角色 → 权限点（`资源:动作`，如 `unified_turn:review`）；
- 接口用 `require_scope` 声明；菜单用 `agent_menu.scope` 控制可见性；
- 超管走 `admin/**`，租户用户走 `tenant/**`；
- 业务域细分到 page/view/review/delete，支持"只读不给删"。

**B14. 为什么用 Outbox + MQ，而不是直接在请求里做？**
- 文档解析、RAGAS 评测耗时长，放请求里会超时；
- Outbox 保证「业务事务提交」与「消息可靠投递」一致（先写 outbox，再由投递器发 MQ）；
- 失败可重试 + 进死信，避免消息丢失。

**B15. 死信队列怎么处理？**
- 消费失败按 retry_count 重试，超上限写 `agent_dead_letter`；
- 支持人工排查后重投；
- 死信落库失败只记日志（不能因为日志丢消息导致死循环）。

## C. 高级（设计取舍与深度）

**C1. 你的「统一编排层」和「各 Agent 图」是怎么划分职责的？**
- 编排层：路由、鉴权、入口校验、上下文压缩、事件映射、写 turn、HITL 恢复入口；
- Agent 图：业务节点（检索/分级/建议/沙箱），不关心 SSE 与存储；
- 好处：业务图可独立演进与测试；编排层不出现 `if agent_type ==`。

**C2. 为什么要做「薄图」而不是把所有节点塞一张图？**
- 各 Agent 的 State 完全不同（qa 是检索字段，评审是 SQL/风险字段）；
- 塞一张图会导致 State 膨胀、条件边爆炸；
- 薄图 + 独立 State 是最小耦合。

**C3. 讲一次你排查过的线上问题（重点准备）。**
推荐讲「检索恒空」：
- 现象：所有 qa 问题都召回为空、走直答；
- 定位：日志 `rag.retrieve.empty tenant=0` → 租户是 0；查 Milvus 分区只有 `'1'`；
- 根因：子图入口 `to_subgraph_input` 只传了 messages，没传 `tenant_id`，节点里 `state.get("tenant_id", 0)` 取默认 0；
- 修复：显式透传 `tenant_id/user_id/session_id/thread_id/trace_id`，并且去掉 `or 0` 兜底（缺失即报错）；
- 加固：检索日志补 `tenant/recall_k/top_score/threshold/hit`，一条日志能判「空召回/低分/精排降级」。

**C4. 还有一次「会话永远只有 1 轮」，怎么查的？**
- 现象：连续对话后轮数仍是 1、无历史、无记忆；
- 查表：turn 只有 1 行；有唯一索引 `(thread_id, turn_index)`；
- 查代码：`_next_turn_index` 依赖的 DAO 方法不存在 → 永远返回 1 → 第二轮插入冲突被 catch 吞掉；
- 修复：改为按 `max(turn_index)+1` 计算，并**去掉吞异常**（写库失败必须暴露）；
- 反思：降级日志救了"服务不 500"，但掩盖了数据丢失，所以关键写入不降级。

**C5. 写库失败为什么选择「不降级」？会有什么代价？**
- 降级的代价是"看起来成功、数据丢了"，排查成本极高（我就是被坑过）；
- 现在：关键写入失败直接抛出，SSE 返回 `error` 帧带 `code/msg`，前端红卡展示；
- 代价：可用性下降（单次失败即失败）；缓解：日志 + trace_id + 明确错误码，让用户能重试。

**C6. RAGAS 指标你了解多少？**
- faithfulness：回答是否被上下文支持（防幻觉）；
- answer_relevancy：回答是否切题（需要 embedding 算生成问题与原问题的相似度）；
- context_precision / context_recall：上下文精确率/召回率（需要标准答案）；
- answer_correctness：与标准答案一致度（事实 + 语义）；
- 陷阱：没有标准答案不能算 context_recall/correctness；没有上下文时 faithfulness 无意义；指标对 prompt 与模型敏感，要固定版本。

**C7. 为什么 RAGAS 必须人工标准答案？**
- context_recall / answer_correctness 都以 reference 为基准；
- 没有 reference 只能算"自洽性"，会给出误导性高分；
- 所以接口强制：非 success 或无答案拒绝、无标准答案拒绝，handler 也二次校验。

**C8. Token 统计你怎么做的？模型不返回 usage 怎么办？**
- 优先用模型返回的 usage（`llm_output.token_usage` 或 `usage_metadata`）；
- 流式下最后一个 chunk 才有 usage，要单独监听 `on_chat_model_end` 累加；
- 网关不返回时按字符估算（中文约 2 字符/token），标记 `estimated`，前端显示 `≈`；
- 明确：估算值不作为计费依据。

**C9. 流式输出 + 人工审批，统计怎么合并不出错？**
- 审批前段：统计写进图状态（`gate_token_usage` / `gate_latency_ms`），不展示；
- 审批后段：resume 时重新累计；
- 最终 `result_card` 输出两段之和，等待时间不计；
- 关键：状态写入要用 `aupdate_state`，且 state schema 要声明这些字段，否则写不进去。

**C10. checkpoint 表膨胀怎么办？**
- 现状：每个 superstep 一条，一轮对话 6~8 条，`checkpoint_blobs` 更大；
- 治理思路：按会话/时间定期归档或清理已结束会话（保留 HITL 挂起中的）；
- 风险：清了会导致 HITL 无法恢复，所以不能无脑级联删除（这也是我删会话只删 thread 的原因）。

**C11. 如何保证「新增一个 Agent 零改动」？**
- `AgentSpec` 是单一真相源：卡片、模板、入口字段、进度标签、scope、事件生成节点；
- 前端按 `event_type` 查渲染器表，不 import 任何 agent；
- registry 自动发现 + DB 覆盖展示名；编排层按 `execution_mode` 分派；
- 验收：加 `db_release` 时前端只加了一个结果卡片渲染。

**C12. 你的可观测体系包含什么？**
- `trace_id` 全链路（HTTP 中间件生成 → 日志 → turn 表 → MQ header）；
- API 调用日志（路径/状态码/耗时/脱敏 header）；
- 业务审计、登录日志（旁路，不阻塞主流程）；
- 看板：请求趋势、调用占比（中文业务标签）、Token 累计、平均耗时；
- Langfuse 可选接入。

**C13. 如果 QPS 上来，你的瓶颈在哪？怎么优化？**
- 瓶颈：LLM 调用（首 token 延迟）、精排（CPU）、Milvus 检索、checkpoint 写入；
- 优化：流式降低感知延迟、精排批量化/GPU、检索缓存（同 query 短 TTL）、模型侧并发限流与超时、把长任务继续拆到 MQ；
- 存储：checkpoint 定期归档、API 日志分区。

## D. 场景与排障题（高频）

**D1. 用户说"检索不到我的文档"，你怎么排查？**
1. `rag.retrieve.empty` 日志看 `tenant` 是否正确、`recall_k` 是否过小；
2. Milvus 该租户分区是否有 chunk（数据是否入库）；
3. `agent_file.parse_status` 是否 `parsed`（解析/OCR 是否失败）；
4. embedding 模型与入库时是否一致（维度/模型名）；
5. 最后才怀疑阈值。

**D2. 用户说"答非所问"，怎么定位？**
- 看 `answer_mode`：`llm_direct` 说明没走 RAG（可能召回空/低分）；
- 看 `top_score` 与 `threshold`：分数低是相关性差（补文档/改切分）；
- 看 `retrieved_contexts`：命中片段是否答非所问（切分粒度/父子片问题）；
- 看 prompt 版本与模型是否变更。

**D3. 接口 403，但用户说给了权限。**
- 查角色权限点是否包含对应 `资源:动作`（如 `unified_turn:review`）；
- 是否超管调租户接口（超管无租户上下文 → 403）；
- 菜单不显示则是 `agent_menu.scope` 未授权或 `visible=false`；
- 前端读的是登录返回的 scopes，需重新登录刷新。

**D4. 审批后没有继续输出。**
- 看 `interrupt` 是否真的产生（图里节点是否执行到）；
- resume 请求的 `thread_id` 必须是子图分区（`{U}:{agent}:{turn}`）；
- checkpoint 是否被清（删会话/清理任务会破坏恢复）；
- 后端日志看 resume 是否 500（DB 写失败现在会直接报错）。

**D5. 会话列表轮数不对/历史缺失。**
- 查 `agent_unified_turn` 是否只有 1 行；
- 查唯一索引 `(thread_id, turn_index)` 是否冲突（序号计算错误）；
- 查写入是否被 `try/except` 吞掉（应改为抛出）。

# 三、反问与加分项

**可以反问面试官**
- 团队当前的 Agent/LLM 应用处于什么阶段（PoC / 生产）？
- 有没有评测体系与线上质量监控？谁负责 prompt 与模型迭代？
- 数据敏感度如何？是否要求私有化部署？

**加分表达（自然带出，不要硬塞）**
- 「关键写库不降级」——体现数据一致性意识；
- 「日志要能一眼判断空召回/低分/精排降级」——体现可观测设计；
- 「知道子图方案的代价」——体现技术选型的权衡能力；
- 「估算 token 但不作为计费依据」——体现边界与严谨。

**避免踩坑**
- 不要把没做的说成做了（如"做了语义记忆召回"——实际只预留 `embedding_id`）；
- 不要夸大模型能力（思考模式依赖模型支持，网关不支持就没有）；
- 被问到不会的，说"这块我只做到 X，Y 是我下一步想验证的"，比编造好。
