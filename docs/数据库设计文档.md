## 0. 阅读说明（给审查者）

- **表来源**：核心 Agent 运行时表 + RBAC/鉴权表 + 配置中心审批流表 + 教育业务域表（试卷、简历、面试、问答、知识库）。
- **身份模型**：本平台自带登录（`user.username` + 明文密码比对），登录签发 JWT；之后每个请求只带 `Authorization: Bearer <JWT>`，身份全部来自 payload——普通用户与租户管理员含 `user_id` + `tenant_id`，超管只含 `user_id`，**请求期不注入任何租户**（`tenant_id` 恒为 `None`）。**超管判定 = 用户位于主租户（`tenant.is_primary`）且该租户内角色名为 `admin`**，只用于校验身份和写审计的归属租户，不参与业务数据过滤；超管只维护基建数据，会话、记忆、QA/chat 等业务链路一律 403。`role_id` 是入库用的整数业务键，只用于库层唯一性兜底（`uk_aut_super_admin` / `uk_aut_tenant_admin`），代码判定一律读 `agent_role.name`。角色/权限始终查库，不信任 token 内的角色快照。`user_id`/`tenant_id` 全部 `BigInteger`（payload 里的字符串形式由 `middleware/auth.py`、`api_log.py` 的 `_parse_int` 转整数）。
- **设计要点**：
  1. **全部逻辑外键**：不建任何物理 `FOREIGN KEY` 约束，引用完整性由代码控制（含 RBAC 的 `role_id` 引用）。
  2. **审计列按「是否与租户相关」收敛**：RBAC/配置/模型等租户无关的表只有 user 审计列；`agent_audit_log`、核心运行时表不带审计四列；业务域表与 `agent_plugin` 保留完整审计四列。
  3. **用户标识**：`agent_long_term_memory`、`agent_escalation` 带 `user_id`；`agent_plugin` 带 `tenant_id` + `user_id`。
  4. **模型配置化**：`agent_model_config` 承载多模型动态配置（LLM API / 本地向量 / 本地重排 / 本地意图识别），由 admin 前端维护；密钥加密入库、单一默认、支持降级链。
  5. **身份与菜单配置化**：`user.username` 为唯一登录名（`name` 为显示名）、`menu.scope` 决定菜单可见性，配合「登录查库 + JWT 单源鉴权」。
  6. **业务域表**沿用参考项目原始结构，待后续优化。

## 1. 总体设计原则

### 1.1 主键策略（三类）

| 类型 | 适用表 | 说明 |
|------|--------|------|
| `UUID`（默认 `uuid_generate_v4()`） | 核心 Agent 表、业务域表、审计/记忆/消息/会话等 | 分布式友好、对外暴露不暴露自增顺序；需 `CREATE EXTENSION "uuid-ossp"`（schema.sql 已包含）。 |
| `BIGSERIAL`（自增整数） | 日志类、配置审批流、角色目录、权限中间表 | 写入量大或纯内部引用，整数主键更紧凑。 |
| 复合主键（业务键） | `agent_user_tenant`(user_id, tenant_id)、`agent_role_permission`(role_id, scope) | 多对多中间表直接用业务键做主键，省去代理键。 |

### 1.2 三个 Mixin（列复用）

| Mixin | 列 | 适用 |
|-------|----|------|
| `TimestampMixin` | `create_at`, `updated_at` | 无审计需求、且自身已带 `tenant_id`/`user_id` 业务列的表：API 日志、配置审批流、`agent_audit_log`、核心运行时表（thread/run/message/tool）、`agent_long_term_memory`、`agent_escalation` |
| `AuditUserOnlyMixin` | `create_at`, `updated_at`, `create_user_id`, `update_user_id` | **租户无关的全局表**，只需记录"谁改的"，不需租户审计列：`agent_role`、`agent_model_config` |
| `AuditMixin`（完整） | `create_at`, `updated_at`, `create_user_id`, `update_user_id`, `create_tenant_id`, `update_tenant_id` | **租户相关且需完整审计**的表：`agent_plugin` + 业务域 10 张表（暂保留参考结构） |

- 时间列默认 `now()`；`updated_at` 由库触发器 `set_updated_at()` 刷新（schema.sql 尾部 22 个 `BEFORE UPDATE` 触发器）。模型上的 `onupdate` 只影响 DDL 语义，运行期不经 ORM，实际刷新全靠触发器。
- 审计列**没有数据库默认值**，由代码写入：`backend/data/sql/audit.py` 的 `audit_on_insert()` / `audit_on_update()` 生成参数，请求期从 `app_state` 上下文取，非请求期必须显式传 `SYSTEM_USER_ID` / `SYSTEM_TENANT_ID`，取不到直接 `RuntimeError`。底线是：宁可不写，也不让审计落到 1001/100 这种占位值上。

> **审计列收敛原则（审查要点）**：是否与租户相关决定 tenant 审计列的去留。全局表（角色目录、配置审批流）只有 user 审计列或根本没有审计列；核心运行时表去掉审计列是因为它们本身已有 `tenant_id` 隔离键与（多数）`user_id` 语义列，再加审计四列冗余。

### 1.3 租户隔离与用户标识

- **`tenant_id BIGINT NOT NULL`** 作为隔离边界出现在：业务域表、核心运行时表、`agent_plugin`。
- **无 `tenant_id` 的全局表**（平台级资源/目录）：`agent_role`、`agent_role_permission`、`agent_config_change_request`、`agent_config_review`、`agent_model_config`、`menu`、`agent`、`user`/`tenant` 自身。
- **`user_id` 类列统一 `BIGINT`**：`user_id`、`tenant_id`、`create_user_id`、`applicant_user_id`、`reviewer_user_id`、`created_user_id`、`resolved_user_id`、`confirmed_user_id`、`reviewed_user_id`、`assigned_user_id` 等一律 `BigInteger`，不再 `String(64)`。
- **用户引用列一律 `*_user_id`**：不存在 `*_by` 后缀列；"处理人/复核人/确认人"这类角色化操作者统一写成 `<角色>_user_id`。
- **逻辑外键**：`agent_user_tenant.(user_id,tenant_id)` 是被全平台 `user_id`/`tenant_id` 引用的"主列"，但**不建物理 FK**，由代码保证引用有效。

### 1.4 数据格式约定

- **JSON 列用 `JSON`（非 `JSONB`）**：与 `agent_api_call_log.req_headers` 一致；当前无 JSONB 索引需求。
- **枚举/状态用 `VARCHAR` + 约定取值**（如 `status`、`op_type`、`action`、`role`），**未加 `CHECK` 约束**——保持与现有风格一致；如需数据严谨可补 `CheckConstraint`。
- **时间列统一 `TIMESTAMP WITHOUT TIME ZONE`**：由应用层保证时区一致（建议服务端 UTC）。

### 1.5 外键策略（全部逻辑外键）

- **无任何物理 `FOREIGN KEY` 约束**（已验证 schema.sql 中 `FOREIGN KEY` 出现次数为 0）。
- 所有跨表引用（包括原 RBAC 的 `agent_role_permission.role_id → agent_role.role_id`、`agent_user_tenant.role_id → agent_role.role_id`）均为**逻辑外键**：列仅作普通字段，引用完整性、级联、脏数据防护由应用层/服务代码控制。
- 理由：降低 schema 耦合，便于分模块演进、灰度与异步写入；代价是需在代码层做引用校验（写入前查主表存在性、删除主记录前清理引用方）。

### 1.6 命名规范

- 表前缀：`agent_`（平台/Agent 运行时与基础设施）、`exam_/interview_/resume_/qa_/knowledge_`（业务域）。
- 时间：`create_at`/`updated_at`；审计：`create_user_id`/`update_user_id`/`create_tenant_id`/`update_tenant_id`。
- 用户标识：一律 `<语义>_user_id`——`user_id`（通用）、`applicant_user_id`/`reviewer_user_id`（配置审批流）、`created_user_id`/`resolved_user_id`/`confirmed_user_id`/`reviewed_user_id`/`assigned_user_id`（业务表内"某角色的操作者"）。**不再出现 `*_by` 后缀**。
- 配置定位：`namespace`/`group_id`/`data_id` 对齐 Nacos 三元组。

> **命名审查点（已统一）**：配置表与业务表的操作者列统一为 `<角色>_user_id`；`assigned_to VARCHAR(64)` 已改为 `assigned_user_id BIGINT`。`agent_thread`/`agent_message`/`agent_run` 补齐 `user_id`，会话与记忆均为「租户 + 用户」二级隔离。

### 1.7 数据访问层（运行时不用 ORM）

表结构只有一份真相（`schema.sql`），代码不复制一份映射关系：

| 层 | 位置 | 职责 |
|---|---|---|
| DDL 模型 | `backend/data/postgres/*.py` | 仅被 `scripts/gen_schema.py` 导入来生成 `schema.sql`，运行期不加载 |
| SQL 基础层 | `backend/data/sql/` | `session_scope()`（复用 `PostgresClient`）、`fetch_all/fetch_one/fetch_value/execute_write`、审计列注入 |
| DAO | `backend/data/dao/` | 每个表/聚合一个 DAO，SQL 以模块级 `text()` 常量内联在文件里 |

约定：

- **不用 ORM 查询**：不出现 `select(Model)`、`session.add(obj)`、`.scalars()`；一切走 `session.execute(text("..."))`。
- **SQL 内联**：不读外部 `.sql` 文件；长 SQL 用 `text("""...""")` 写在 DAO 文件顶部，就近审查。
- **返回 dict**：查询结果经 `mappings()` 转成 `dict[str, Any]`，数据层不构造实体对象；需要强类型时由业务层自己转。
- **参数化**：一律 `:name` 绑定，不拼字符串；`uuid` / `jsonb` 这类参数要显式 `CAST(:x AS uuid)` / `CAST(:x AS jsonb)`，否则驱动推断不出类型。
- **UUID 入参**：先校验格式（见 `ThreadDao._as_uuid`），非法值直接判「不存在」，避免类型错误把 404 变成 500。
- **审计列**：见 §1.2，统一由 `audit_on_insert()` / `audit_on_update()` 生成参数。

迁移状态（2026-10-24）：**已完成**。`backend/data/postgres/` 只剩模型类，运行期不加载；业务代码里已无 `select(Model)` / `session.add()`，`before_flush` 审计事件已删除。DAO 一览：

| DAO | 覆盖表 |
|---|---|
| `thread_dao.py` | `agent_thread` |
| `api_log_dao.py` | `agent_api_call_log` |
| `agent_dao.py` | `agent`、`agent_capability_policy` |
| `config_dao.py` | `agent_config_change_request`、`agent_config_review` |
| `rbac_dao.py` | `agent_role`、`agent_role_permission`、`agent_user_tenant`、`tenant` |

## 3. 各表详细设计

### 3.0 user / tenant / menu（身份与菜单，运行时读取）

**用途**：`user` 是**登录认证主表**；`tenant` 提供租户显示名；`menu` 是菜单下发的数据源（`scope` 列按权限过滤）。

#### 3.0.1 user（账号）

| 字段 | 类型 | 必填 | 默认 | 约束/索引 | 说明 |
|------|------|------|------|-----------|------|
| id | BIGSERIAL | ✅ | — | PK | 用户ID（与全局 `user_id` 对齐） |
| username | VARCHAR(64) | ✅ | — | `uk_user_username` UNIQUE | **登录名**，登录只查该列 |
| name | VARCHAR(64) | ✅ | — | — | 显示名（前端展示/日志用），**不参与登录**，不再要求唯一 |
| password | VARCHAR(128) | ✅ | — | — | **明文密码**，登录时直接字符串比对（不哈希、不加盐） |
| tenant_id | BIGINT | ✅ | — | `ix_user_tenant_id` | 主租户（登录时默认选中；真实授权以 `agent_user_tenant` 为准） |

- `user` 是 PostgreSQL 保留字，模型已 `quote=True`，DDL 生成为 `"user"`；手写 SQL 里也要写成 `"user"`。
- 与 `agent_user_tenant` / RBAC 之间**无外键约束**，仅逻辑关联（遵循全库"逻辑外键"策略）。
- 完整登录/鉴权流程见 `docs/登录与权限校验说明.md`：`username + password` → 查 `agent_user_tenant` 拿租户与角色 → 过滤 `menu`。
- 默认数据（密码统一 `123456` 且明文存储；只有 1001 是超管，位于主租户 100）：

| id | username | name | tenant_id | 备注 |
|---|---|---|---|---|
| 1001 | admin | admin | 100 | 100 → role_id=3（超管，唯一） |
| 2001 | admin-a | school-a 管理员 | 200 | 200 → role_id=5 |
| 2002 | teacher-test | teacher-test | 200 | 200 → role_id=2 |
| 2003 | student-b | student-b | 200 | 200 → role_id=1 |
| 3001 | admin-b | school-b 管理员 | 300 | 300 → role_id=5 |

> 每个账号都必须有 `agent_user_tenant` 分配，否则登录时在「查分配」一步 403。主租户 100 只保留 `admin` 一个用户。

#### 3.0.2 tenant（租户）

| 字段 | 类型 | 必填 | 默认 | 约束/索引 | 说明 |
|------|------|------|------|-----------|------|
| id | BIGSERIAL | ✅ | — | PK | 租户ID |
| name | VARCHAR(64) | ✅ | — | — | 租户显示名 |
| enabled | BOOLEAN | ✅ | `true` | — | 是否启用；停用后不可登录、不可切换，数据保留 |
| is_primary | BOOLEAN | ✅ | `false` | `uk_tenant_primary`（部分唯一索引，`WHERE is_primary`） | 主租户标记；超管判定 = `is_primary` 且角色名 `admin`（`role_id=3` 仅作库层唯一性兜底） |

默认：`100=主租户`（`is_primary=true`）/ `200=school-a` / `300=school-b`，初始全部 `enabled=true`。

#### 3.0.3 menu（菜单）

| 字段 | 类型 | 必填 | 默认 | 约束/索引 | 说明 |
|------|------|------|------|-----------|------|
| id | BIGSERIAL | ✅ | — | PK | 菜单ID |
| name | VARCHAR(64) | ✅ | — | — | 菜单名称（前端展示） |
| path | VARCHAR(128) | ✅ | — | — | 前端路由路径 |
| icon | VARCHAR(64) | ✅ | `''` | — | 图标名（如 `DashboardOutlined`） |
| parent_id | BIGINT | ✅ | `0` | — | 父菜单ID（0=顶级） |
| sort_order | INTEGER | ✅ | `0` | — | 排序号（升序） |
| visible | BOOLEAN | ✅ | `true` | — | 是否显示 |
| scope | VARCHAR(64) | ❌ | NULL | — | 访问所需权限点；NULL=登录即可见 |

- 过滤规则：`visible=true` AND（`scope IS NULL` OR `scope ∈ 用户 scopes` OR 用户含 `*`）AND 父菜单可见。
- 菜单只控制入口显隐，**不是安全边界**；接口侧仍需 `require_scope`。

### 3.1 agent_user_tenant（用户-租户-角色分配）

**业务背景**：平台身份权威表。用户在某租户下拥有唯一角色（`role_id`）。由网关断言 `user_id`/`tenant_id` 写入，后端鉴权时据此判定角色与权限。

| 字段 | 类型 | 必填 | 默认 | 约束 | 说明 |
|------|------|------|------|------|------|
| user_id | BIGINT | ✅ | — | PK | 用户ID（网关断言，BigInteger） |
| tenant_id | BIGINT | ✅ | — | PK | 租户ID（隔离边界，BigInteger） |
| role_id | INTEGER | ✅ | — | — | 该用户在租户内的唯一角色（整数业务键；**逻辑外键→agent_role.role_id，代码控制**） |
| created_at | TIMESTAMP | ✅ | now() | — | 分配时间 |

**业务背景**：角色元数据（如 `student`/`teacher`/`admin`），全局共享，不绑定租户。

| 字段 | 类型 | 必填 | 默认 | 约束 | 说明 |

- **审计列收敛**：角色为全局目录，与租户无关，故使用 `AuditUserOnlyMixin`，**仅保留 `create_user_id`/`update_user_id`**，去掉 `create_tenant_id`/`update_tenant_id`。

- **默认角色种子**：`schema.sql` 末尾内联 RBAC 默认数据，以整数 `role_id` 写入 4 个内置角色（`1=student` / `2=teacher` / `3=admin` / `5=tenant_admin`，`4` 随 `analyst` 角色删除而空缺、不复用）及其权限点；运行时 `security/rbac.py` 的 `DEFAULT_ROLES` 与之完全一致。脚本整体采用 `CREATE TABLE/INDEX IF NOT EXISTS` + `DROP TRIGGER IF EXISTS` 策略，重复执行不会删除已有表，幂等安全。
- **角色作用域**：`3=admin` 只允许出现在主租户（`tenant.is_primary=true`），是平台超管，`scopes` 为 `*`；`5=tenant_admin` 每租户至多一个，管本租户用户与角色，**不含** `agent:*`、`model:*`、`tenant:write`。
- **权限点配置**：teacher（`role_id=2`）含 `qa:read`，「会话运行」菜单对其可见；`tenant:read` / `tenant:write` 供超管维护租户；`rbac:read` / `rbac:write` 超管全局、租户管理员限本租户；`agent:read` / `agent:write` / `model:read` / `model:update` 仅超管。`DEFAULT_ROLES` 与种子必须一致，否则会出现「库里有、代码不认」或相反。

### 3.16 agent_model_config（模型配置）——设计稿，未落地

> 本节为设计稿：模型与 `schema.sql` 尚未包含该表，`/api/v1/models/**` 也无实现。落地时按 §0 的命名与审计列规范补 `backend/data/postgres/` 模型并重新生成脚本。

**业务背景**：平台要同时接入多个模型——远程 LLM API（如 `deepseek-chat`）、本地向量模型（`bge-m3`）、本地重排（`bge-reranker-v2-m3`）、本地意图识别（`bert-chinese`）。这些模型名/地址/密钥原先散落在 `.env` 的 `MODEL.*`，改一次要重启。本表把模型变成**可运维数据**：admin 前端增删改查、设默认、探测连通性；运行时按 `model_type` 取默认实例，改完热更新。

**设计取舍**：

- **平台级全局（无 `tenant_id`）**：模型属基础设施资源，按租户配模型会把密钥与配额管理复杂化；如需租户差异，另加策略表（§3.16.1 预留），不动主表。
- **密钥不入明文**：密钥只存 AES-GCM 密文 + 掩码；密钥材料来自 env `MODEL_SECRET_KEY`，不入库、不下发前端。
- **同类唯一默认**：同一 `model_type` 只允许一个 `is_default=true`，否则运行时"用哪个"不确定。

| 字段 | 类型 | 必填 | 默认 | 约束/索引 | 说明 |
|------|------|------|------|-----------|------|
| id | BIGSERIAL | ✅ | — | PK | 主键 |
| code | VARCHAR(64) | ✅ | — | `uk_model_code` UNIQUE | 业务键，代码中引用（如 `deepseek-chat`、`bge-m3-local`），**稳定不改** |

**索引与约束**：

```sql
UNIQUE (code);                                                          -- uk_model_code
CREATE INDEX ix_model_type ON agent_model_config (model_type, enabled, priority);
CREATE UNIQUE INDEX uq_model_default ON agent_model_config (model_type) WHERE is_default AND enabled;
```

- `uq_model_default` 是**部分唯一索引**：每个 `model_type` 最多一个「启用且默认」。设为默认时事务内先 `UPDATE ... SET is_default=false WHERE model_type=?`，再置新值。
- `fallback_code` 为逻辑自引用（全库无物理 FK），服务层写入前校验目标存在且无环（A→B→A）。

**业务规则**：

1. **同类唯一默认**：`is_default=true AND enabled=false` 视为无效（索引已排除），运行时跳过该条。
2. **删除保护**：被 `fallback_code` 引用、或本身是默认的，拒绝删除（409），提示改为停用。
3. **密钥只写不读**：响应仅回 `api_key_masked`；更新时 `api_key` 传空=保持不变，传值=重新加密并刷新掩码。
4. **热更新**：写库成功后调 `LLMFactory.reload(model_type)`；多副本靠定时刷新（`MODEL_REFRESH_SECONDS`，默认 60s）对齐，允许短暂差异。
5. **降级链**：`resolve(model_type)` 取默认实例，失败按 `fallback_code` 回退；全链失败抛 `ModelError`，**不静默回落到 env**（避免"改了库以为生效"）。
6. **高风险操作留痕**：增删改/设默认同时写 `agent_audit_log`（`action='model.update'`、`target=code`）。
7. **维度联动（易踩）**：`embedding.params.dense_dim` 必须与 Milvus collection 的向量维度一致。切换 embedding 默认模型若维度不同，必须重建 collection 并全量重索引，不能只改库——建议默认模型切换接口对维度变化直接拒绝，要求走「新建 collection + 双写迁移」流程。
8. **意图模型标签集**：`intent.params.labels` 是分类输出契约，改动顺序必须与下游路由映射一致；建议只允许追加标签，删除标签前先确认无存量数据引用。

## 5. 关键设计决策与审查要点

1. **全部逻辑外键（无物理 FK）**：彻底去耦合，便于分模块演进；代价是引用完整性由代码保证。审查：需确认服务层在写入/删除时做存在性校验与级联清理。

2. **审计列按租户相关性收敛**：
   - 全局/租户无关表（`agent_role`）仅 `create_user_id`/`update_user_id`。
   - 自带 `tenant_id`/`user_id` 的表（`agent_audit_log`、核心运行时表）**去全部审计四列**，避免冗余。
   - 仅 `agent_plugin` 与业务域表保留完整四列（前者是租户资源需审计；后者依第 7 条暂保留）。

3. **会话/记忆的 user_id**：`agent_thread`（会话所有者，另建 `(tenant_id, user_id)` 联合索引）、`agent_message`/`agent_run`（冗余自会话）、`agent_long_term_memory`、`agent_escalation` 均带 `user_id BIGINT`，与租户构成二级隔离。Redis 短期记忆 key 同步为 `t:{tenant}:u:{user}:session:{thread}`，Milvus 长期记忆按 `tenant_id + user_id` 过滤。身份上下文缺失时记忆读写直接跳过，宁可不记也不跨用户串。

4. **插件租户隔离**：`agent_plugin` 新增 `tenant_id` + `user_id`，保留审计四列；`UNIQUE(name)` 维持全局唯一（如需租户内并存改为 `(name, tenant_id)` 待定）。未来由前端显式维护每租户可用插件。

5. **user_id/tenant_id 统一 BigInteger**：所有引用列 `BIGINT`，网关字符串由 middleware 转整数。**审查**：网关须实际下发整数；否则写入失败。

6. **审计列无默认值（已完成）**：`create_user_id`/`update_user_id`/`create_tenant_id`/`update_tenant_id` 去掉 `DEFAULT 1001`/`DEFAULT 100` 且保持 `NOT NULL`。写入入口统一为 `backend/data/sql/audit.py` 的 `audit_on_insert()` / `audit_on_update()`——请求期从上下文注入，非请求期必须显式传值，漏填即 `RuntimeError`。种子数据显式写 1001/100。

7. **命名统一（已完成）**：配置表与业务表的操作者列统一为 `<role>_user_id`；`assigned_to VARCHAR(64)` 改为 `assigned_user_id BIGINT`（可空）。

8. **无 CHECK 约束**：状态/类型枚举用 `VARCHAR` + 约定值，未加 `CHECK`；应用层须严格校验。如需强约束可补 `CheckConstraint`。

9. **JSON 而非 JSONB**：与现有风格一致；如需 JSON 内索引/去重换 `JSONB`。

10. **业务域表暂保留**：依第 7 条，10 张业务表沿用参考项目原始结构（含完整审计四列），待后续优化（见 §3.17~3.25 待优化项）。

11. **模型配置从 env 迁到表（`agent_model_config`）**：解决"改模型名/密钥要重启"的问题。要点：全局单表（无 `tenant_id`）、同类型唯一默认（部分唯一索引）、密钥密文+掩码、`fallback_code` 降级链、写库后热更新（`LLMFactory.reload`）。审查：需确认 `MODEL_SECRET_KEY` 在生产由 KMS/密钥管理下发，且轮换时能批量重加密。

12. **登录名与显示名分离**：`user.username` 承担登录（唯一索引），`user.name` 转纯展示名。`name` 不再唯一，避免"改名必须改登录名"的耦合；代价是改名不影响登录，需注意两列同步维护。

13. **菜单权限化**：`menu.scope` 与 `agent_role_permission.scope` 同词汇表（`资源:动作`），筛选在服务端完成，前端只渲染返回结果，不再硬编码菜单。

```sql
    last_probe_ok BOOLEAN,
    last_probe_msg VARCHAR(512),
    remark VARCHAR(512),
    create_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT now(),
    updated_at TIMESTAMP WITHOUT TIME ZONE NOT NULL DEFAULT now(),
    create_user_id BIGINT NOT NULL,
    update_user_id BIGINT NOT NULL
);

CREATE UNIQUE INDEX IF NOT EXISTS uk_model_code ON agent_model_config (code);
CREATE INDEX IF NOT EXISTS ix_model_type ON agent_model_config (model_type, enabled, priority);
CREATE UNIQUE INDEX IF NOT EXISTS uq_model_default
    ON agent_model_config (model_type) WHERE is_default AND enabled;
```

> 说明：`updated_at` 为三个 Mixin 的列名，与存量表一致；新表需一并纳入 `set_updated_at()` 触发器的生成范围（`gen_schema.py` 默认覆盖）。
